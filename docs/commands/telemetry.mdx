---
title: "lucy telemetry"
description: "Control telemetry and inspect local upload statistics"
---

Lucy alpha and beta builds enable telemetry by default. Telemetry helps maintainers understand command usage and diagnose operational failures. The data is pseudonymous (random and non-identifying UUIDs). Cloudflare processes network addresses when it receives uploads, and privacy filtering cannot guarantee that every sensitive detail is removed.

The first telemetry-enabled command in human-readable mode prints a one-time notice that explains collection and how to opt out.

## Control collection

```bash
lucy telemetry          # show the current state
lucy telemetry off      # stop collection and clear pending local records
lucy telemetry on       # enable collection
lucy telemetry stats    # show local upload statistics
lucy telemetry reset-id # generate a new client ID and reset local statistics
```

Turning telemetry off deletes pending local records but keeps the client ID and upload statistics. It does not delete data already received by the service. Resetting the ID does not change or delete remote data or pending records; pending records retain the ID under which they were collected. Uploads of those records count in the new statistics period. Statistics cover this local client only; they are not a statement of what the service still stores.

The service retains command events and their structured snapshots, plus diagnostic reports, for 30 days from receipt. Retention starts when the service receives a record, not when the command ran, so a record queued for a week still receives the full window. Locally queued records expire after 7 days if they cannot be uploaded.

Set `DO_NOT_TRACK=1` to disable collection and uploads for a process, such as a CI job. This does not change the saved preference or clear the queue.
Local development builds skip telemetry collection and uploads, including queued records from release builds. `LUCY_TELEMETRY_ENDPOINT` overrides the upload destination for release builds. Use a trusted HTTPS endpoint; reserve HTTP for loopback testing. `lucy telemetry stats` shows the configured destination.

## What lucy collects

A command event contains the command path, `lucy` version and build, operating system and architecture, duration when measured, outcome, an error category, and whether lucy detected a coding agent. It does not contain raw command lines, arbitrary argument text, typed input, paths, URLs, environment values, search text, or file contents. A randomly generated client ID links events from this installation; it is not derived from hardware or a workspace path, and lucy does not create a cross-process session identifier. The invocation ID joins one event, its snapshots, a local diagnostic log, and any automatic failure or panic report from the same run.

Lucy may attach small typed snapshots that describe:

- The invocation shape: whether the command line was accepted; the flags this execution changed and the positional slots it used, recorded as bounded names with a kind. Only inputs the command declares as a boolean, a number, a normalized version, or a selector from a fixed vocabulary contribute a value. A text input is never promoted because its spelling matches, and text and list values are omitted.
- Execution: coarse phase timings for stages lucy already tracks, such as setup, resolution, downloads, installation, and identification, plus the active phase, a cancellation reason, a failure kind, cumulative time spent waiting for interactive input, the largest file count observed, and cumulative time waiting for its file locks and for the package service to respond. These samples can overlap each other and the phase timings.
- Workspace and runtime: when already observed, the product, product version, Minecraft version, and package count; the Java major version, version, and distribution; and whether an agent tool was detected.

Each snapshot records whether lucy observed the data, did not observe it, or failed to observe it, and a reason for a missing snapshot. A missing value is not a zero count. Snapshots are short markers, not report bodies. Operational failures can trigger a private diagnostic report with invocation-scoped, filtered lucy diagnostic information; a report can carry captured stage messages and a stack, while the event carries only bounded markers. Only product failures and panics trigger automatic reports. Lucy does not trigger discovery, network probes, or workspace scans to fill a snapshot. It does not upload Minecraft server logs, configuration files, full package inventories, or complete command lines.

Diagnostic reports are private: their metadata and body go to maintainers, and the service retains them for 30 days from receipt. The local diagnostic log stays on your machine.

Coding agents may submit a privacy-filtered report about a failure or other friction, not only a command failure. `lucy agent-report` takes the report body as its only argument, and `--agent` and `--model` name the harness and model when known. Lucy tells agents to write one to three sentences: the command, the error code or observed behavior, and the expected result, leaving out secrets, absolute paths, logs, transcripts, and user data. An agent reports each distinct problem once and then continues the task. It skips a failure caused by its own wrong directory, wrong flag, or missing prerequisite, but reports unexpected behavior even when a workaround exists. Lucy also redacts common secret and path patterns and truncates oversized bodies. It rejects reports when telemetry is off. An agent must not turn telemetry on unless you explicitly instruct it to do so.

## Uploads and statistics

Lucy queues records locally and sends bounded batches when the service is reachable. A queued record keeps its identity and occurrence time, so a later attempt sends the same record rather than a new one. If the connectivity check or an upload fails, lucy waits for a cooldown before trying again on a later invocation. Lucy uploads only while a command runs, so an offline record stays queued until the next invocation. `--offline` suppresses the upload for that run but still queues its event.

The service may decline an upload under its intake budget. Statistics count intake-limited upload attempts; they do not identify unique records lost, because a later attempt can still deliver the same record.

An invalid command line is recorded as a usage error, separately from a product failure. Lucy cannot tell a typo from a deliberate test, a script probe, or generated help, so it preserves the usage outcome without guessing intent. Successful help, version, and other guidance-only runs stay local. Product reporting leaves usage errors out of the failure headline and shows them as a separate invalid-usage count.

Statistics start when the client ID is created or reset. They separate accepted event payload and report content sizes from request-body bytes handed to the HTTP transport. Request-body bytes include retries but exclude HTTP and TLS overhead; an interrupted process may not record its final attempt. Accepted totals count each record once and do not guarantee remote retention. The same view counts records dropped locally by the queue bounds or expiry, records the service permanently rejected, intake-limited upload attempts, and attempts whose acceptance is uncertain.
