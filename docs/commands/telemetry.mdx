---
title: "lucy telemetry"
description: "Control telemetry and inspect local upload statistics"
---

Lucy alpha and beta builds enable telemetry by default. Telemetry helps maintainers understand command usage and diagnose operational failures. The data is pseudonymous (random and non-identifying UUIDs). Cloudflare processes network addresses when it receives uploads, and privacy filtering cannot guarantee that every sensitive detail is removed.

The first telemetry-enabled command in human-readable mode prints a one-time notice that explains collection and how to opt out. Lucy records that it showed the notice, so it does not appear again on the same machine.

## Control collection

```bash
lucy telemetry          # show the current state
lucy telemetry off      # stop collection and clear pending local records
lucy telemetry on       # enable collection
lucy telemetry stats    # show local upload statistics
lucy telemetry reset-id # generate a new client ID and reset local statistics
```

Turning telemetry off deletes pending local records but keeps the client ID and upload statistics. It does not delete data already received by the service. Resetting the ID does not change or delete remote data or pending records; pending records retain the ID under which they were collected. Uploads of those records count in the new statistics period. Statistics cover this local client only; they are not a statement of what the service still stores.

The service retains event records and their snapshots for 30 days and diagnostic reports for 14 days. Locally queued records expire after 7 days if they cannot be uploaded.

Set `LUCY_TELEMETRY=off` to disable collection and uploads for a process, such as a CI job. This does not change the saved preference or clear the queue.
Local development builds do not collect or upload telemetry, including queued records from release builds. `LUCY_TELEMETRY_ENDPOINT` overrides the upload destination for release builds. Use only a trusted HTTPS endpoint; HTTP is permitted only for loopback testing. `lucy telemetry stats` shows the configured destination.

## What lucy collects

A command event contains the command name, `lucy` version and build, operating system and architecture, duration when measured, outcome, an error category, and whether lucy detected a coding agent. It does not contain argument values, flag values, typed input, paths, URLs, environment values, or search text. A randomly generated client ID links events from this installation; it is not derived from hardware or a workspace path, and lucy does not create a cross-process session identifier. The invocation ID joins one event, its snapshots, a local log, and any automatic failure or panic report from the same run.

Lucy may attach small typed snapshots that describe:

- The invocation shape: whether the command line was accepted, a positional-argument count, the output mode, offline mode, and the names and kinds of flags from a fixed allowlist. A flag outside the allowlist is omitted instead of recorded.
- Execution: coarse phase timings for stages lucy already tracks, such as setup, resolution, downloads, installation, and identification, plus the active phase, a cancellation reason, a failure kind, and whether the run took 30 seconds or longer. Lucy may also record cumulative time waiting for its file locks and for the package service to respond. Those samples can overlap each other and the phase timings.
- Prompts: whether prompts were available, the run was non-interactive or had no terminal, or the mode was unknown, how many prompts appeared, the total time prompts were open, whether a form was aborted by the user, and whether the surrounding run was interrupted while a form was open.
- Counts: how many packages, requested packages, files, completed files, or candidates a command had already counted.
- Recoverable warnings, and whether the invocation ID appears in a local diagnostic log. The log itself is never uploaded.

Each snapshot records whether lucy observed the data, did not observe it, or failed to observe it, and a reason for a missing snapshot. A missing snapshot is not a zero count. Snapshots are short markers, not report bodies. Operational failures can trigger a private diagnostic report with invocation-scoped, filtered lucy diagnostic information; a report can carry captured stage messages and a stack, while the event carries only bounded markers. Successful and canceled runs do not trigger automatic reports. Their snapshots are the only detailed timing evidence. Lucy does not trigger discovery, network probes, or workspace scans to fill a snapshot.

When a command already observes server or Java information, lucy may include the existing limited structured snapshot for it. Lucy does not automatically upload Minecraft server logs, configuration files, full package inventories, or complete command lines.

Coding agents may submit a privacy-filtered report about a failure or other friction, not only a command failure. `lucy agent-report` takes the report body as its only argument, and `--agent` and `--model` name the harness and model when known. Lucy tells agents to write one to three sentences: the command, the error code or observed behavior, and the expected result, leaving out secrets, absolute paths, logs, transcripts, and user data. An agent reports each distinct problem once and then continues the task. It skips a failure caused by its own wrong directory, wrong flag, or missing prerequisite, but reports unexpected behavior even when a workaround exists. Lucy also redacts common secret and path patterns and truncates oversized bodies. It rejects reports when telemetry is off. An agent must not turn telemetry on unless you explicitly instruct it to do so.

## Uploads and statistics

Lucy queues records locally and sends bounded batches when the service is reachable. A queued record keeps its identity and occurrence time, so a later attempt sends the same record rather than a new one. If the connectivity check or an upload fails, lucy waits for a cooldown before trying again on a later invocation. It does not run a background service, so an offline record may remain queued until lucy runs again. Telemetry failure does not change the result of your command.

The uploader stamps delivery metadata on an event upload attempt: how long the record waited in the outbox, the attempt count, and how many throttled responses it received. These values describe delivery, not command time, and a retry with different metadata is not a second record. The service may also decline an upload under its intake budget. Budget counters count declined delivery attempts; they do not identify unique records lost, because a later attempt can still deliver the same record.

An invalid command line is recorded as a usage error, separately from a product failure. Lucy cannot tell a typo from a deliberate test, a script probe, or generated help, so it preserves the usage outcome without guessing intent. Successful help, version, and other guidance-only runs are not queued. Product reporting leaves usage errors out of the failure headline and shows them as a separate invalid-usage count.

Statistics start when the client ID is created or reset. They separate accepted event payload and report content sizes from request-body bytes handed to the HTTP transport. Request-body bytes include retries but exclude HTTP and TLS overhead; an interrupted process may not record its final attempt. Accepted totals count each record once and do not guarantee remote retention. The same view counts records dropped locally by the queue bounds or expiry, records the service permanently rejected, intake-limited upload attempts, and attempts whose acceptance is uncertain.
