---
title: "Workflow diagnostics"
description: "Explain Lucy failures and state changes from structured results, read-only probes, and diagnostic logs"
---

Diagnose from evidence, not from a retry. A machine-mode failure already carries a stable code, a title, details, and a log path. A successful install-style result carries the decision it made. Use read-only commands to compare declared, locked, and live state before mutating again.

## Triage order

1. Read the failure document on stderr. Branch on `code`, then use `title` and `details` to identify the exact case.
2. If the command wrote a result before failing, inspect the workspace files named in the title; failure documents do not carry partial results.
3. Run `lucy status` and `lucy status --from-lock` to compare live state with the lock.
4. Read the log file named by `log`, or the default log path, for the decision trail.
5. Only then retry, and only with the flag that addresses the cause.

## Exit status and failure codes

Command failures exit `1`. Ctrl-C and termination normally exit `130` after cleanup. `lucy docs grep` uses `2` for usage errors and unmatched patterns are `1`; it is the exception to the general command exit contract.

| Code | Meaning | First check |
| --- | --- | --- |
| `usage.invalid_invocation` | Command line, flag, or argument rejected before the action | `hint`, then `lucy <command> --help` or `lucy docs` |
| `usage.unsupported_output` | The command has no JSON result, or `schema` cannot describe it | Run without JSON, or choose a command from `lucy schema` |
| `command.failed` | Unclassified action failure | `title`, `details`, then the log |
| `operation.cancelled` | Context cancelled or deadline exceeded | Whether cleanup completed; retry only if safe |
| `resolve.no_matching_build` | One version request matched no build | The hint often names a concrete version to pin |
| `resolve.no_compatible_build` | Builds exist, but none fit this server | `details` for per-build rejection groups |
| `status.lock_missing` | `status --from-lock` had no lock to read | Run `lucy install`, or use live `lucy status` |
| `status.read_failed` | Working directory or lock could not be read | Filesystem permissions and cwd |
| `status.selection_failed` | A runtime selection error that made live status unusable | The log and `lucy status` details |
| `info.*` | Package lookup, reference, provider, or local artifact failure | The specific `info` code and hint |

For resolution failures, `resolve.no_matching_build` means exactly one version-mismatch group was reported; `resolve.no_compatible_build` covers every other rejection, including multiple groups and aborted searches. Read `details` before changing a selector: the same code can mean a missing version, an incompatible loader, or an unsatisfied module requirement.

## Read install-style results

`install`, `add`, `remove`, `init`, `create`, and applied `upgrade` share the install result. These fields explain behavior that the exit status does not:

| Field | Evidence |
| --- | --- |
| `mode` | `replay` did not resolve a new lock; `resolve` did; `locked` rebound requirements against the same server core |
| `reason` | Why the mode was chosen, such as `manifest changed since lock`, `no lock file to replay`, `optional packages requested`, `manifest unchanged; lock replays exactly`, or `manifest core matches; requirements rebind in place` |
| `published_manifest`, `published_lock` | Which documents were actually written |
| `packages[].change` | `added`, `removed`, `upgraded`, `downgraded`, `rebuilt`, or `changed` |
| `manifest_changes` | Selectors rewritten by resolution or upgrade, with previous and new values |
| `server.change` | `added` or `upgraded` for the server core, plus previous and current versions |
| `files` | Managed runtime outputs created, replaced, or removed |
| `fetch` | Artifacts reused from cache or downloaded, and bytes transferred |
| `diagnostics` | Tracked-file findings, each with `path` and `message` |
| `warnings` | Non-fatal module, ownership, and compatibility findings |
| `java` | Selected runtime and `problems`; absent when selection never ran |
| `total_packages` | Total packages recorded by the committed lock |

There is no `changed` boolean. Compute it from the server, package, manifest, file, and publication fields. A result with no changes still means the command succeeded.

`reason: "manifest unchanged; lock replays exactly"` with `mode: "replay"` means no catalogue resolution occurred, but missing artifacts may still be fetched. `mode: "resolve"` with `published_lock: true` means the desired state changed the lock; inspect `manifest_changes` and `packages` before committing that lock in an automated flow.

## Read-only probes

### Status

`lucy status` observes the live directory. `source` is `live`, `activity` is `running`, `stopped`, or `unknown`, and paths are relative to `root`. An empty workspace, an ambiguous runtime, or a missing declared installation can still produce a successful report; the finding is in `warnings`. Do not treat exit `0` as proof that a runtime was selected.

`lucy status --from-lock` renders the lock instead. `source` is `lock`, `entry_point` is empty, and `activity` is `unknown` because the lock cannot prove runtime state. It fails with `status.lock_missing` when there is no lock.

### Dependencies

`lucy tree` and `lucy leaves` read the lock by default and fall back to a live probe when the lock is missing or invalid. Their `origin` field is `lock file` or `live probe`. Add `--live` to skip the lock entirely. Use these when `status` shows packages but you need to know which artifact or native module pulled them in.

### Java

`lucy java list` reports the locked requirement, the selected runtime, every installed runtime, and each runtime's unmet constraints in `problems`. A configured `java.home` is honored even when it misses requirements; Lucy warns instead of silently choosing another runtime. If `install` selected no usable runtime, its `java` field has no `runtime` and lists `problems`.

### Tracked files

`lucy file list` compares declared files with working contents. A modified immutable file produces a warning that names `lucy file update` and `lucy file recover`. Use `lucy file history` to inspect the event and revision sequence before accepting or restoring bytes.

## Workspace files as evidence

Inspect these files read-only; never hand-edit them while a mutation runs.

| Path | Role |
| --- | --- |
| `lucy.yaml` | Declared intent. Top-level `manifest_version` and `server`, plus optional `mcdr` and `files`. Package keys are `provider:project` under an ecosystem group; selectors are `any`, `stable`, `beta`, or an exact version. |
| `lucy-lock.yaml` | Resolved facts. `lock_version`, `manifest_fingerprint`, `server`, optional `mcdr`, flat `packages`, optional `files`. The server records product, core version, artifact hashes, bootstrapper, inputs, and Java advisory; each package records environment, ecosystem, provider, project, release, file, version, filename, URL, SHA-256, and requirements. |
| `.lucy/install.yaml` | Runtime ownership receipt: `version`, `lock_fingerprint`, and entries with `path`, `sha256`, and `mode`. Pruning only removes paths recorded here. |
| `.lucy/commit.yaml` | Install journal. Its presence means a transaction was interrupted; the next mutation rolls it back before proceeding. |
| `.lucy/history/files.jsonl` | File tracking event history, read by `lucy file history`. |
| `.lucy/config.yaml` | Workspace configuration, including `java.home`; managed by `lucy config`. |
| `.lucy/writer.lock` | Active writer marker; its presence with a live process explains a concurrency failure. |

The lock's `manifest_fingerprint` must match the current manifest for replay. `lucy install` compares it and reports the outcome as `mode` and `reason`; an automated flow should use those fields rather than recomputing the fingerprint.

## Log evidence

Every command writes a diagnostic log. The default is `~/Library/Logs/lucy/lucy.log` on macOS, `~/.local/share/lucy/logs/lucy.log` on Linux, and `%APPDATA%\lucy\logs\lucy.log` on Windows. The file always receives debug records, even when `--log-level` raises the terminal mirror. `--log-level` accepts `debug`, `info`, `warn`, `error`, or `fatal`; it affects only what `--print-logs` mirrors.

In machine mode, `--print-logs` is suppressed so stderr keeps its single-document contract. Read the log file instead. Set `--log-file` per job when several workspaces run on one machine; the default file is shared and append-only.

Search for these records to reconstruct a workflow:

| Message | Meaning |
| --- | --- |
| `action invoked` | Command path and working directory at entry |
| `installation decision` | Chosen `mode` and `reason` before resolution or replay |
| `staging installation` | A new runtime tree is being staged; the reason is `installation missing or stale` or `manifest publication forces re-staging` |
| `installation current` | The installation receipt matches the lock and every owned output |
| `installation already current` | The resolved lock is current and no staging is needed |
| `installation not current` | A receipt is absent, the lock fingerprint changed, or an owned output is missing or modified |
| `lock resolution reused current lock` | Resolution ran but the existing lock still matched the manifest |
| `recovering interrupted installation transaction` | A previous install journal is being rolled back at the start of a mutation |
| `installation transaction recovered` | Recovery finished before the new operation proceeded |
| `removed stale staging file` | Abandoned staging data was reclaimed under the writer lock |

The log does not replace the result document. It explains decisions and boundaries; the JSON result is the contract.

## Common signatures

| Signature | Cause and response |
| --- | --- |
| `another Lucy operation owns this workspace` | Another process holds `.lucy/writer.lock`. Wait, then retry; never parallelize mutations. |
| `stop the running Minecraft server before installation` or `before changing tracked files` | Stop the server, then rerun. Do not bypass the guard. |
| `unowned or modified output conflict` | A destination is occupied or changed. Inspect it; move it aside, adopt it with `lucy init`, or use `--overwrite` only when replacement is intended. |
| `no Java runtime` | Install a runtime, run `install --java`, or set `java.home` through `lucy config set`. `java list` shows why installed runtimes do not fit. |
| `locked installation requires a current lucy-lock.yaml` or `manifest changed since the lock` | Resolve once without `--locked`, inspect the new lock, then commit it. |
| `lock changed during package selection; retry from current state` | Another writer changed the lock. Retry after it exits. |
| `lucy-lock.yaml is required; run lucy install first` | `upgrade` needs a current lock; run an install to produce one. |
| `several server runtimes share this directory` | `init` cannot choose in machine mode. Use one of the `--entry-point` commands in `details`. |
| `the declared server installation is missing` | Run `lucy install --locked`; if the declaration is wrong, adopt the remaining runtime with `init --force --entry-point`. |
| `immutable contents differ` | Inspect with `file list`. Accept the change with `file update` or restore with `file recover`. |
| `compile does not support JSON output` | Run `compile` without JSON flags; stdout carries the artifact path. |
| `doctor: not implemented yet` or `export: not implemented yet` | These commands are advertised but unimplemented. Use `status`, `tree`, `leaves`, `java list`, `file list`, and the log instead. |

## Escalate with evidence

When a failure is not covered by these signatures, collect all of the following before changing state:

- The failure document, including `code`, `title`, and every `details` entry.
- The relevant `status` and `status --from-lock` documents.
- The install-style result, if the command produced one.
- The tail of the log file at the path in `log`, especially `action invoked`, `installation decision`, and any `installation not current` or recovery records.

That set distinguishes a bad invocation, a resolution failure, a stale lock, an ownership conflict, and an interrupted transaction without running the same command again.
