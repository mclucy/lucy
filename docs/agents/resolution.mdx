## From requirements to pins

Manifest parsing decodes and normalizes the declaration before calculating its fingerprint. The lock records that fingerprint alongside the resolved server, optional MCDReforged runtime, flattened package artifacts, and tracked-file declarations. Package records retain bindings to direct requirements and dependency provenance. Lock validation requires concrete package versions, filenames, and SHA-256 hashes.

Installation compares the declaration with the existing lock to decide whether it can replay the lock or must resolve. A lock can also be replayed without a manifest; that installation registers a lock-only entry in the server registry so artifact collection can discover its references. When resolution is needed, an existing compatible server or package pin can be reused; a changed declaration does not automatically mean every artifact is upgraded. Offline mode cannot perform fresh metadata resolution. An upgrade command can request a fresh resolution even if the lock matches the manifest.

Server resolution determines the server product, core artifact, bootstrap profile, inputs, and Java version advisory. Package resolution selects package candidates against the target runtime, prior pins, declared requirements, and dependency metadata. Descriptors within artifacts are inspected for loader-specific modules, and their constraint dialects are evaluated. The resolver merges declarations that select the same artifact while retaining their requirement bindings and dependency relationships.

The lock is the authoritative package resolution for a declaration. A dependency graph can be derived from the lock's resolved packages, or from a live observation when no valid lock is available; it analyzes relationship structures without mutating lock, receipt, or workspace state.

The package resolver restores each selection and its incompatibility declarations together when backtracking. Search passes start with empty branch state but share candidate, identity, and artifact-analysis caches.

One artifact may declare several modules under one identity. A wrapper that bundles one nested jar per Minecraft line ships every variant with disjoint requirements on the server's own modules, and the loader loads the variant the running version satisfies. The module index therefore prefers the variant that serves the target before comparing versions, and keeps version order when the choice is not forced or the modules come from different artifacts. Requirements another package answers never decide a variant.

Upstream capability interfaces separate search, metadata retrieval, version selection, artifact fetching, dependency resolution, and hash identification. A provider need not implement every capability. Routing maps the requested provider or ecosystem to the relevant implementations, passing local runtime facts through structured context rather than giving providers direct access to workspace discovery or interactive prompts.

The resolver receives candidate lookup and artifact materialization as injected capability functions, plus an optional cache that reuses artifact analysis across candidates; descriptor reading remains a dedicated archive inspection. The resolver does not select a provider or open the network cache. Installation and operation workflows receive configured capabilities at construction; operation options can supply prefetched artifact bytes without changing catalog selection. They still extract the server core's descriptor modules to supply as target constraints. Installation strictly verifies supplied bytes against the artifact's pinned hashes.

## From pins to installed files

Synchronizing an installation acquires the workspace writer lock, performs preflight checks and interrupted-install recovery, decides the resolution mode, and passes the resulting lock to staging. Planning separates resolution from execution: the installation plan records manifest and lock fingerprints, and execution checks them before staging so a concurrent document edit cannot be silently overwritten.

Staging materializes locked server inputs and enabled package artifacts, selects Java, and prepares the server tree through bootstrap adapters. Package destinations must not alias on the target filesystem. Installation and in-place adoption commit staged files and documents atomically using the transaction journal (`.lucy/commit.yaml`). The receipt (`.lucy/install.yaml`) is the authoritative local ledger recording committed runtime paths lucy owns, their concrete origins, and separate bootstrap identity and package resolution fingerprints; tracked-file declarations and Java requirements do not invalidate that receipt.

The installation journal records before and after content and permission images for each changed path, with backups relative to the workspace, strictly separated from the committed receipt. Staged, synced replacements and pre-commit image checks prevent partial writes and silent overwrites. Replay requires an inactivity check confirming that the workspace root and declared server directories are stopped; replay runs this check once after journal detection and before any mutation, so a workspace with no pending journal needs no runtime check. Journal replay reverses recorded changes only when filesystem images match and refuses to overwrite intervening edits. After the receipt is published, a committed marker makes recovery cleanup-only; a cleanup failure does not roll back the installation. All pruning of superseded files routes through this ordinary transaction path rather than parallel post-commit cleanup.

An existing output is never safe to replace by content equality, missing receipt, or directory scope alone. Ownership is granted solely by installation commit or explicit initialization adoption. Initialization records ownership for recognized packages and proven runtime files without running bootstrap installers, rechecking observed files before atomic publication; unidentified or ambiguous files remain unowned. The recorded SHA-256 in the receipt acts as a conflict baseline protecting local edits rather than a reproducibility pin: a new bootstrap or package install may produce different valid bytes, provided any existing managed file matches its accepted baseline before replacement. Modified managed files are never silently overwritten or pruned, and re-initialization preserves existing modification baselines. Seed files are initialized when missing and remain user-owned, so subsequent seed edits never invalidate bootstrap currentness or grant pruning authority. Tracked working files remain outside runtime ownership and pruning, sharing layout classification between preflight and post-staging checks.

If the receipt and owned outputs satisfy bootstrap and package currentness, lucy skips runtime staging; manifest publication never forces restaging of an otherwise satisfied runtime. Bootstrap currentness uses a single shared method-verification path across staged outputs and adopted trees, evaluating contract satisfaction rather than byte equality with prior runs. It still checks unmanaged artifacts and handles MCDReforged and tracked-file provisioning where applicable. After a successful installation commit, tracked-file provisioning may report diagnostics or fail; the result may therefore describe a failure after the runtime was committed.

## Downloads and state

The installation artifact store is a per-user content-addressed store outside the workspace, fed by verified bytes from the shared network cache or upstream downloads. Locked hashes identify expected bytes; the store, like the network cache, is not the manifest, lock, or ownership receipt. A registered server is retained because its lock pins artifacts, not because it owns files in the store. Working-file tracking maintains a separate workspace-local object store for tracked-file revisions. Confusing these stores can lead to incorrect assumptions about what a lock can restore on another machine.
