## From requirements to pins

Manifest parsing decodes and normalizes the declaration before calculating its fingerprint. The lock records that fingerprint alongside the resolved server, optional MCDReforged runtime, flattened package artifacts, and tracked-file declarations. Package records retain bindings to direct requirements, dependency provenance, and the declared relationships of the selected release. Lock validation requires concrete package versions, filenames, and SHA-256 hashes.

Installation compares the declaration with the existing lock to decide whether it can replay the lock or must resolve. A lock can also be replayed without a manifest; that installation registers a lock-only entry in the server registry so artifact collection can discover its references. When resolution is needed, an existing compatible server or package pin can be reused; a changed declaration does not automatically mean every artifact is upgraded. Offline mode cannot perform fresh metadata resolution. An upgrade command can request a fresh resolution even if the lock matches the manifest.

A downgrade uses the locked package version as its baseline and keeps the server and MCDReforged runtime unchanged. It replaces the requested direct roots' selectors in a cloned manifest and resolves against prior pins. Unaffected packages retain compatible pins; dependency resolution can still backtrack, but each chosen target build is its project's only candidate. An incompatible target fails rather than falling back to another version. A stale lock or an unreadable required core artifact aborts planning. The installation plan records the original document fingerprints, so concurrent edits are rejected before publication. Applying the plan uses the ordinary installation transaction and its post-commit provisioning semantics.

Recording optional dependencies adds only previously undeclared references. Existing direct selectors, file patterns, and enabled state remain authoritative when dependency metadata adds another binding for the same reference.

Server resolution determines the server product, core artifact, bootstrap profile, inputs, and Java version advisory. Package resolution selects package candidates against the target runtime, prior pins, declared requirements, and dependency metadata. Descriptors within artifacts are inspected for loader-specific modules, and their constraint dialects are evaluated. The resolver merges declarations that select the same artifact while retaining their requirement bindings and dependency relationships.

The lock is the authoritative package resolution for a declaration. A dependency graph can be derived from the lock's resolved packages, or from a live observation when no valid lock is available; it analyzes relationship structures without mutating lock, receipt, or workspace state.

The package resolver restores each selection and its incompatibility declarations together when backtracking. Search passes start with empty branch state but share candidate, identity, and artifact-analysis caches.

Package resolution normally rejects module and upstream metadata incompatibilities. Downgrade's force mode accepts package-only problems during the first search and reports conflicts from the final selected graph as warnings. Runtime requirements, hard candidate filters, and operational failures remain fatal. This differs from broken-graph acceptance, which retries with all module checks relaxed.

One artifact may declare several modules under one identity. A wrapper that bundles one nested jar per Minecraft line ships every variant with disjoint requirements on the server's own modules, and the loader loads the variant the running version satisfies. The module index therefore prefers the variant that serves the target before comparing versions, and keeps version order when the choice is not forced or the modules come from different artifacts. Requirements another package answers never decide a variant.

Upstream capability interfaces separate repository candidates and build listing, search, project metadata, and artifact identification. A provider that identifies an artifact by hash answers with the release itself, so adoption reads what is installed instead of listing the project's releases. Candidates carry the provider's compatibility and dependency evidence; resolution has no generic package-fetch path.

### Package sources

Providers share these interfaces but not the metadata behind them. Routing dispatches a candidate request only to a registry that has a package catalogue, and the selected provider rejects an ecosystem it cannot serve.

- Modrinth supplies candidate artifacts with hashes and dependency declarations, and implements hash identification. CurseForge supplies the same candidate and dependency capabilities when its API key configures the provider, and also implements hash identification.
- Hangar accepts an `owner/slug` path, a bare slug that resolves to one project, or a numeric project ID; the immutable numeric project ID is preferred once found. Candidates are platform-specific: a Bukkit or Paper request takes the Paper download, and versions are filtered against Hangar's declared Paper `platformDependencies`. Hangar also publishes Waterfall and Velocity downloads, but no package target requests them. When Hangar declares no platform compatibility, the candidate is kept with compatibility marked unknown. Hangar plugin dependencies are usable only when they name a Hangar project and carry its project ID without an external URL; an entry that links outside Hangar marks the dependency metadata incomplete. Download metadata may carry a SHA-256 digest.
- Package resolution identifies a Spiget resource by its numeric SpigotMC ID; a display name is accepted only when exactly one resource matches it. Its catalogue exposes no per-version Minecraft version, loader, release channel, checksum, or dependency declarations. Candidates therefore mark compatibility and dependency metadata as unknown; resolution warns about compatibility, and about the dependency gap whenever it expands dependencies, rather than treating the gaps as "compatible" or "no dependencies". Resource-level tested versions describe the resource as a whole, not one published version, and are not used as candidate evidence. Only the resource's current version is installable: Spiget's version-specific download endpoint redirects to a SpigotMC page that rejects automated clients, while the resource-level endpoint always serves the newest file. Older versions may remain visible as metadata, but adding one or re-resolving a manifest pinned to one fails because candidates list only the current version. Upgrade is the exception: it advances `any`, `beta`, or an exact old selector to the current build and rewrites an exact pin; `stable` is rejected because the channel is unknown. Upgrade fails and leaves the lock unchanged when no current build exists or the current build no longer uses the locked artifact URL. Externally hosted resources are likewise limited to their single current-version URL. The lock pins the SHA-256 lucy computes from the fetched bytes, and replay fails if the mutable current-version URL later serves different bytes.
- Hash identification is not available for Hangar or Spiget. Their packages are resolved from an explicit project reference, never by matching local bytes to an upstream project.

Candidate filtering belongs to providers because only they know their own compatibility fields. The resolver filters by the fields a candidate carries and never invents missing metadata.

The resolver receives candidate lookup and artifact materialization as injected capability functions, plus an optional cache that reuses artifact analysis across candidates; descriptor reading remains a dedicated archive inspection. The resolver does not select a provider or open the network cache. Installation and operation workflows receive configured capabilities at construction; operation options can supply prefetched artifact bytes without changing catalog selection. They still extract the server core's descriptor modules to supply as target constraints. Installation strictly verifies supplied bytes against the artifact's pinned hashes.

## From pins to installed files

Synchronizing an installation acquires the workspace writer lock, performs preflight checks and interrupted-install recovery, decides the resolution mode, and passes the resulting lock to staging. Planning separates resolution from execution: the installation plan records manifest and lock fingerprints, and execution checks them before staging so a concurrent document edit cannot be silently overwritten.

Staging materializes locked server inputs and enabled package artifacts, selects Java, and prepares the server tree through bootstrap adapters. Package destinations must not alias on the target filesystem. Installation and in-place adoption commit staged files and documents atomically using the transaction journal (`.lucy/commit.yaml`). The receipt (`.lucy/install.yaml`) is the authoritative local ledger recording committed runtime paths lucy owns, their concrete origins, and separate bootstrap identity and package resolution fingerprints; tracked-file declarations and Java requirements do not invalidate that receipt.

Package placement is derived from the lock's server and wrapper layout. Installation, ownership checks, unmanaged-package scans, and lock-based status use that same authority: Bukkit-family content belongs in `plugins/`, loader content in `mods/`, and MCDReforged content in its wrapper's `plugins/`. Placement does not establish that a package is enabled or installed.

The installation journal records before and after content and permission images for each changed path, with backups relative to the workspace, strictly separated from the committed receipt. Staged, synced replacements and pre-commit image checks prevent partial writes and silent overwrites. Replay requires an inactivity check confirming that the workspace root and declared server directories are stopped; replay runs this check once after journal detection and before any mutation, so a workspace with no pending journal needs no runtime check. Journal replay reverses recorded changes only when filesystem images match and refuses to overwrite intervening edits. After the receipt is published, a committed marker makes recovery cleanup-only; a cleanup failure does not roll back the installation. All pruning of superseded files routes through this ordinary transaction path rather than parallel post-commit cleanup.

An existing output is never safe to replace by content equality, missing receipt, or directory scope alone. Ownership is granted solely by installation commit or explicit initialization adoption. Initialization records the packages and runtime files it recognizes, checks the observed bytes again before atomic publication, and runs no bootstrap installer; a file stays unowned when no provider identifies it, when several installed files identify the same project, when its matched release has no download URL, lists no loader the server runs, does not support a dedicated server, or has no project ID, when the server does not load its ecosystem, or when its descriptor cannot be read or declares no server-side module. An adopted release wins for its reference even when its labels name another Minecraft version; the mismatch is reported. The recorded SHA-256 in the receipt acts as a conflict baseline protecting local edits rather than a reproducibility pin: a new bootstrap or package install may produce different valid bytes, provided any existing managed file matches its accepted baseline before replacement. Modified managed files are never silently overwritten or pruned, and re-initialization preserves existing modification baselines. Seed files are initialized when missing and remain user-owned, so subsequent seed edits never invalidate bootstrap currentness or grant pruning authority. Tracked working files remain outside runtime ownership and pruning, sharing layout classification between preflight and post-staging checks.

If the receipt and owned outputs satisfy bootstrap and package currentness, lucy skips runtime staging; manifest publication never forces restaging of an otherwise satisfied runtime. Bootstrap currentness uses a single shared method-verification path across staged outputs and adopted trees, evaluating contract satisfaction rather than byte equality with prior runs. It still checks unmanaged artifacts and handles MCDReforged and tracked-file provisioning where applicable. After a successful installation commit, tracked-file provisioning may report diagnostics or fail; the result may therefore describe a failure after the runtime was committed.

## Downloads and state

The installation artifact store is a per-user content-addressed store outside the workspace, fed by verified bytes from the shared network cache or upstream downloads. Locked hashes identify expected bytes; the store, like the network cache, is not the manifest, lock, or ownership receipt. Spiget artifacts key network-cache entries by provider, hashed URL, project, release, and file instead of the URL alone; because a Spiget download URL is mutable and not version-specific, a URL-only key could return bytes from an earlier release. A registered server is retained because its lock pins artifacts, not because it owns files in the store. Working-file tracking maintains a separate workspace-local object store for tracked-file revisions. Confusing these stores can lead to incorrect assumptions about what a lock can restore on another machine.
