## From requirements to pins

`document` decodes and normalizes the manifest before calculating its fingerprint. The lock records that fingerprint alongside the resolved server, optional MCDReforged runtime, flattened package artifacts, and tracked-file declarations. Package records retain bindings to direct requirements and dependency provenance. Lock validation requires concrete package versions, filenames, and SHA-256 hashes.

`install` compares the declaration with the existing lock to decide whether it can replay the lock or must resolve. A lock can also be replayed without a manifest; that installation registers a lock-only entry so artifact collection can see its references. When resolution is needed, an existing compatible server or package pin can be reused; a changed declaration does not automatically mean every artifact is upgraded. Offline mode cannot perform fresh metadata resolution. Upgrade can request a fresh resolution even if the lock matches the manifest.

Server resolution in `upstream/routing` determines the product, artifact, bootstrap profile, inputs, and Java advisory. `resolve.Packages` selects package candidates against the target runtime, prior pins, declared requirements, and dependency metadata. `artifact` reads loader-specific descriptors; `version` interprets their constraint dialects. The resolver merges declarations that select the same artifact while retaining their requirement bindings and dependency relationships.

The package resolver restores each selection and its incompatibility declarations together when backtracking. Search passes start with empty branch state but share candidate, identity, and artifact-analysis caches.

One artifact may declare several modules under one identity. A wrapper that bundles one nested jar per Minecraft line ships every variant with disjoint requirements on the server's own modules, and the loader loads the variant the running version satisfies. The module index therefore prefers the variant that serves the target before comparing versions, and keeps version order when the choice is not forced or the modules come from different artifacts. Requirements another package answers never decide a variant.

Upstream interfaces separate search, information, version selection, fetching, dependencies, and hash identification. A provider need not implement every capability. Routing maps the requested provider or ecosystem to the relevant implementations; it passes local runtime facts as `upstream.LocalContext`, rather than giving providers access to workspace discovery or prompting.

The resolver receives candidate lookup separately from artifact materialization and descriptor-analysis memoization. It does not select a provider or open the network cache. `install.Service` and `operation.Service` receive configured capabilities at construction; operation options can supply prefetched artifact bytes without changing catalogue selection. Installation verifies supplied bytes against the artifact's pinned hashes.

## From pins to installed files

`install.Service.Sync` acquires the workspace writer lock, performs preflight checks and interrupted-install recovery, decides the resolution mode, and passes the resulting lock to staging. `install.Service.PlanInstall` separates resolution from application: the plan records manifest and lock fingerprints, and `ApplyPlan` checks them before staging so a concurrent document edit cannot be silently overwritten.

Staging materializes locked server inputs and enabled package artifacts, selects Java, and calls `bootstrap` to prepare the server tree. Package destinations must not alias on the target filesystem. Installation commits the staged files and documents with a rollback journal. The receipt records owned runtime outputs and a fingerprint of the server, MCDReforged, and package resolution; tracked-file declarations and Java requirements do not invalidate that receipt.

The installation journal records before and after content and permission images for each changed path, with backups relative to the workspace. Staged, synced replacements and pre-commit image checks prevent partial writes and silent overwrites. Recovery reverses journaled changes only when their images match and refuses to overwrite intervening edits. After the receipt is published, a committed marker makes recovery cleanup-only; a cleanup failure does not roll back the installation. Unreferenced rollback directories are not removed by name alone.

An existing output is not automatically safe to replace. Ownership, matching contents, explicit overwrite selection, and an installation adopted through discovery affect the commit decision. Initialization records ownership for each package it identifies from upstream metadata, so a version change replaces that file and prunes the old destination even though initialization staged nothing. A package initialization leaves unidentified stays unowned. A previously owned output that was modified cannot simply be pruned. Tracked working files are excluded from runtime ownership and pruning.

If the receipt and owned outputs are current, lucy can skip runtime staging. It still checks unmanaged artifacts and handles MCDReforged and tracked-file provisioning where applicable. After a successful installation commit, tracked-file provisioning may report diagnostics or fail; the result may therefore describe a failure after the runtime was committed.

## Downloads and state

The installation artifact store is a per-user content-addressed store outside the workspace, fed by verified bytes from the shared network cache or the network. Locked hashes identify expected bytes; the store, like the cache, is not the manifest, lock, or ownership receipt. A registered server is retained because its lock pins artifacts, not because it owns files in the store. `filetrack` has a separate workspace-local object store for tracked-file revisions. Confusing these stores can lead to incorrect assumptions about what a lock can restore on another machine.

Relevant entry points: `install/install_plan.go`, `install/install_resolve.go`, `install/install_workspace.go`, `install/install_transaction.go`, `resolve/resolve_packages.go`, and `upstream/routing`.
