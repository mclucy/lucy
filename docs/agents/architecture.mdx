Lucy maintains several views of a server. They answer different questions and are not interchangeable:

| View | Authority | Meaning |
| --- | --- | --- |
| Declaration | `lucy.yaml` | Desired server and package requirements, including tracked-file policy and the optional registry name. |
| Resolution | `lucy-lock.yaml` | Concrete server inputs and package artifacts selected for a declaration. |
| Installation receipt | `.lucy/install.yaml` | Runtime outputs Lucy recorded as installed, their hashes, and the resolution they answer. |
| Observation | Files in the workspace | What discovery can establish about the local runtime and package files now. |
| Artifacts | Per-user artifact store | Verified bytes pinned by the locks of registered servers; the network cache is separate and expires. |
| Machine configuration | Global and workspace config | Local runtime preferences, separate from portable server intent. |

A lock can describe files that are absent or modified locally; an observed file is not necessarily owned by Lucy or identified with a registry project. A manifest change does not itself establish a new lock or installed state. Local configuration does not change the manifest fingerprint.

## Boundaries

The command layer translates CLI input into operations and renders their results. `operation` coordinates use cases and document changes. `install` resolves or replays a lock, stages and commits runtime files, and returns facts and warnings to the command layer. `workspace` observes local state without contacting upstreams; identification against upstream hashes is an explicit separate step.

`artifactstore` owns the durable per-user content store for installed artifacts and the conservative reclamation sweep over registered servers' locks. It composes `cas` with `serverregistry`; it does not own workspace state. `catalog` holds package identities, artifacts, and dependencies without owning workspace state. `server` describes server products and environments. `serverregistry` maps the user's server names to workspace directories through entry files in the user data directory (symlink entries created by earlier versions remain readable); it records locations, not server contents, and reads each registered manifest or lock on demand. A lock-only entry has no selectable name but still lets collection find its artifact references. `upstream` defines capabilities for obtaining metadata and artifacts; `upstream/routing` selects implementations, and `upstream/providers` contains provider-specific adapters. `resolve` chooses packages and validates their descriptor modules. `bootstrap` prepares server products from the locked inputs. Java requirements and runtime observation belong to `javaruntime`, while machine settings belong to `config`.

## Invocation ownership

`cmd.Runner` owns a fresh command tree, streams, presentation values, and diagnostic logger. `Execute` receives the caller's context; the executable owns signal handling, and `Runner.Close` releases the cache store, diagnostics, and owned HTTP connections. Server selection changes `cli.Invocation.Directory`, not the process working directory. Command paths and machine settings resolve against that directory.

The command boundary constructs configured `cache.Client`, `routing.Router`, `install.Service`, and `operation.Service` instances after parsing flags and selecting the workspace. The CLI's typed dependency assembly stays in the command layer; backend services receive their own narrow dependencies. Provider catalog assembly performs no HTTP requests or credential decoding. Reports, themes, and progress renderers use invocation-owned streams and terminal capabilities.

`.golangci.yml` enforces the package boundaries through depguard. `task lint` is part of local and CI checks. Concrete provider imports stay in provider adapters and routing composition; resolution consumes candidate lookup and materialization capabilities, while workspace observation remains upstream-free.

## Package identity is not module identity

A registry project and release identify an artifact to download. A descriptor inside that artifact identifies one or more modules that the Minecraft loader sees. Descriptor dependency constraints refer to those module IDs, not necessarily the registry project name. Artifact metadata alone does not establish its registry provenance; hash identification can associate local bytes with an upstream project when a provider supports it.

A locked package combines an artifact pin with its environment, ecosystem, and requirement bindings. Multiple declarations may bind to the same artifact. A dependency can keep a package enabled even when a direct binding is disabled. Consequently a row in the lock is not, by itself, proof that the file is installed.
