Lucy maintains several views of a server. They answer different questions and are not interchangeable:

| View | Authority | Meaning |
| --- | --- | --- |
| Declaration | `lucy.yaml` | Desired server and package requirements, including tracked-file policy and the optional registry name. |
| Resolution | `lucy-lock.yaml` | Concrete server inputs and package artifacts selected for a declaration. |
| Installation receipt | `.lucy/install.yaml` | Runtime outputs lucy recorded as installed or as explicitly adopted during initialization, their conflict baseline hashes, and the bootstrap identity and package resolution fingerprints they answer. |
| Observation | Files in the workspace | What discovery can establish about the local runtime and package files now. |
| Artifacts | Per-user artifact store | Verified bytes pinned by the locks of registered servers; the network cache is separate and expires. |
| Machine configuration | Global and workspace config | Local runtime preferences, separate from portable server intent. |

A lock can describe files that are absent or modified locally; an observed file is not necessarily owned by lucy or identified with a registry project. A manifest change does not itself establish a new lock or installed state. Local configuration does not change the manifest fingerprint.

## Boundaries

The command layer translates CLI input into operations and renders their results. The operation layer coordinates use cases and document changes. Installation resolves or replays a lock, stages and commits runtime files, and returns facts and warnings to the command layer. Workspace observation inspects local state without contacting upstream networks; identifying local files against upstream hashes is an explicit separate step.

The artifact store manages the durable per-user content-addressed storage for installed artifacts and runs conservative reclamation sweeps across registered server locks. It does not own workspace state. The installation receipt records committed outputs and answers separate bootstrap identity and package resolution fingerprints; installation, tracked-file verification, and discovery read this document through a single schema decoder. The server registry maps server names to workspace directories through entry files in the user data directory, tracking locations rather than server contents and reading registered manifests or locks on demand. A lock-only registry entry has no selectable name but allows garbage collection to discover its artifact pins.

Upstream capability interfaces define contracts for metadata retrieval, artifact downloads, version discovery, and hash identification. Upstream routing dispatches across multiple provider implementations while keeping provider-specific adapters isolated. Package resolution selects compatible artifacts and validates loader descriptor modules. Server bootstrap prepares launchable server products from locked inputs. Portable Java requirements derived from server products and packages are distinguished from local runtime selection, which discovers host installations and honors local machine configuration.

The dependency graph derives package relationships from a lock, or from a live observation when no valid lock is available, to answer traversal queries such as roots, leaves, and topological ordering. It returns graph facts to the command layer for rendering or to the bisect subsystem, which manages persisted bisection sessions, captured manifests, range toggling, and installation synchronization.

A runtime inactivity guard prevents modifying active servers and serves as the recovery entry point for interrupted installations. It detects pending transactions and verifies that the workspace root and server directories are stopped before initiating journal replay; replay runs this check after detection and before any filesystem mutation. Tracked-file modifications and pending recovery apply the same inactivity check before mutating state.

## Invocation ownership

Each CLI execution instantiates a fresh command tree with dedicated output streams, presentation values, and diagnostic logging. The process lifecycle manages signal handling, and execution shutdown cleanly releases cache stores, diagnostics, and open HTTP connections. Server selection targets a specific workspace directory rather than mutating the process working directory; command paths and machine settings resolve against that targeted directory.

The command boundary constructs configured caching, upstream routing, installation, and operation services after evaluating flags and selecting the workspace. Service dependencies remain narrow and explicitly assembled; provider catalog assembly performs no network requests or credential decoding. Reports, themes, and progress renderers bind directly to invocation-owned streams and terminal capabilities.

Architectural boundaries keep concrete provider implementations isolated behind routing composition and capability interfaces. Package resolution consumes abstract candidate lookup and artifact materialization capabilities, while workspace observation remains strictly local and upstream-free.

## Package identity is not module identity

A registry project and release identify an artifact to download. A descriptor inside that artifact identifies one or more modules that the Minecraft loader sees. Descriptor dependency constraints refer to those module IDs, not necessarily the registry project name. Artifact metadata alone does not establish its registry provenance; hash identification can associate local bytes with an upstream project when a provider supports it. Modrinth and, when configured, CurseForge implement hash identification; Hangar and Spiget artifacts are identified only by an explicit project reference.

A locked package combines an artifact pin with its environment, ecosystem, and requirement bindings. Multiple declarations may bind to the same artifact. A dependency can keep a package enabled even when a direct binding is disabled. Consequently a row in the lock is not, by itself, proof that the file is installed.
