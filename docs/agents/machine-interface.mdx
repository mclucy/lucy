Use this page to call `lucy` from an agent or CI job. The [command guides](/commands/global-flags) cover human-facing usage.

## Read the installed documentation

The binary carries the documentation pages for its own version. `lucy docs` is hidden from normal help, but it works without a workspace or network:

```bash
lucy docs list
lucy docs view commands/install
lucy docs view agents/machine-interface
```

Page names are archive paths without `.mdx`. `list` prints them in sorted order. `view` accepts a leading `/` and a trailing `.mdx`, but otherwise needs the exact slug.

Search the corpus with `lucy docs grep`:

```bash
lucy docs grep -n 'published_lock' agents/workflows agents/diagnostics
lucy docs grep -l 'resolve.no_matching_build'
lucy docs grep -F 'stop the running Minecraft server'
lucy docs grep -e 'mode' -e 'reason' agents/diagnostics
```

- Without `-e`, the first positional argument is the pattern and the rest are page filters.
- With `-e`, every positional argument is a page filter. Filters are exact slugs, not directories.
- Patterns are Go regular expressions unless `-F` selects fixed strings. `-i`, `-w`, and `-x` apply to either form.
- `-l` prints matching page slugs, `-L` prints non-matching slugs, and `-c` prints per-page counts.
- `-A`, `-B`, and `-C` add context; `-n` adds line numbers. `-h` suppresses filename prefixes and `-H` forces them. `-h` is not help for `grep`; use `--help`.
- Exit status is `0` when a line matches, `1` when nothing matches, and `2` for invalid patterns, pages, or flags. `-q` stops at the first match.

`docs` ignores `--json` and `--json-compact`; its output is raw page text. Do not wrap it in a JSON parser.

## Defaults in agent sessions

When Lucy detects a coding-agent harness, it changes two defaults for that process:

- `--no-interactive` becomes `true`.
- `--json-compact` becomes `true` for commands that have a JSON result, unless the command line already names `--json` or `--json-compact`.

Explicit flags win. In automation, pass both flags explicitly instead of relying on detection:

```bash
lucy install --locked --json-compact --no-interactive
```

Prompts never open while JSON output is selected, even if `--no-interactive=false` is passed. Machine mode also disables progress rendering and the `--print-logs` terminal mirror. The log file still receives records.

Outside JSON mode, `--no-interactive` fails a command that needs a choice instead of prompting, and the error names the flag that carries the same choice. There is no global confirmation flag such as `--yes`; use the command's selection flags, such as `--minecraft` for `create`, `--entry-point` for `init`, or `--all` for `upgrade`.

`--help` remains human-oriented. Prefer `lucy docs` for prose, `lucy schema` for field-level contracts, and JSON output for command results.

## Streams and exit status

In machine mode the streams have one document each:

| Result | Exit status | stdout | stderr |
| --- | --- | --- | --- |
| Success | `0` | One JSON result document | Empty |
| Failure | Non-zero | Empty | One JSON failure document |
| Interrupt | Usually `130` | Empty | One JSON failure document if the command reached its boundary |

`--json` indents with two spaces. `--json-compact` prints one line and wins when both are set. Treat the process status as the authority and parse only the selected stream; never parse human output. Results are published only after cleanup succeeds, so a killed process can leave neither a complete result nor a complete failure document.

Warnings that belong to a result travel inside that document instead of stderr. They do not change the exit status. Failure documents have this shape; `lucy schema --error` is the authoritative schema for the running binary:

```json
{
  "schema": 1,
  "kind": "error",
  "code": "resolve.no_compatible_build",
  "title": "<human-readable summary>",
  "details": ["<detail line>"],
  "hint": "<optional next step>",
  "log": "<path to the diagnostic log>"
}
```

`code` is the stable field for branching. `title`, `details`, and `hint` are explanations for a person. `log` is always present. See [Workflow diagnostics](/agents/diagnostics) for the code families and the log evidence behind them.

Commands without a JSON result are not interchangeable with machine-mode commands:

- `compile` rejects `--json` and `--json-compact` with `usage.unsupported_output` before starting a build. Its human stdout is the artifact path.
- `docs` ignores the JSON flags and emits page text.
- `schema` always emits JSON, with or without the JSON flags.
- `doctor` and `export` are advertised but not implemented; they fail instead of producing a result.

## Discover JSON contracts

`lucy schema` describes the machine output of the running binary without reading a workspace or using the network:

```bash
lucy schema
lucy schema install
lucy schema upgrade
lucy schema create
lucy schema status
lucy schema file
lucy schema file history
lucy schema --error
```

- `lucy schema` lists every command path that has a result contract.
- A command group, such as `lucy schema file`, lists its supported descendants.
- A leaf, such as `lucy schema install`, returns its JSON Schema.
- A command with several result shapes returns an `anyOf` schema. `upgrade` is one: applied upgrades and dry-run frontiers have different documents.
- A command without a result, such as `compile` or `docs`, fails with `usage.unsupported_output`.
- `lucy schema --error` returns the shared failure schema and accepts no command path.
- `lucy schema` always emits JSON. `--json-compact` makes it one line; human output is not available.

The schema reflects the installed version, so prefer it over hard-coded field lists when a command may change.

## Workspace scope and concurrency

Every workspace command except `create --directory` uses the current working directory as its workspace. Run commands with the intended working directory; there is no global workspace flag.

Mutating commands take a writer lock at `.lucy/writer.lock`. Install commands, `add`, `remove`, `upgrade`, `init`, `create`, and mutating `file` subcommands must not be run in parallel in one workspace. A second writer fails with a `command.failed` document whose title contains:

```text
another Lucy operation owns this workspace
```

Wait for the first process to exit, then retry. Read-only commands such as `status`, `tree`, `leaves`, `info`, `search`, `file list`, `file history`, `java list`, `docs`, and `schema` can run while a writer works, though their view may be stale.

`install`, `upgrade`, and mutating `file` subcommands require the Minecraft server to be stopped. They fail with a title that starts with `stop the running Minecraft server`; `status` is safe while it runs.

Do not edit `lucy.yaml` or `lucy-lock.yaml` while a mutation runs. A mutation that is killed is recovered at the start of the next mutating command; the recovery is recorded in the log as `recovering interrupted installation transaction`.

A successful mutation means the command committed, not that it changed files. Inspect the result fields such as `published_manifest`, `published_lock`, `files`, and `packages` to see what moved.
