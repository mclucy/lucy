---
title: "Network cache and content storage"
description: "Request indexing, artifact verification, expiration, and distinct object-store lifecycles"
---

The network cache stores reusable network responses separately from a workspace. Its index maps a canonical request key to an entry with a content digest, filename, kind, integrity metadata, size, and expiration. The bytes live in a content-addressed store addressed by SHA-256. Several request keys can refer to the same object.

Metadata and artifacts have separate policy limits and lifetimes. The default metadata refresh period is four hours and the artifact retention period is seven days; request-specific metadata can choose a different TTL. Expiration affects whether an indexed response can be reused, not the meaning of a lock or receipt.

A read-only POST lookup opts into caching; its key digests method, URL, body, and headers, so lookup bodies and credentials never share responses and state-changing POSTs stay uncached. Metadata requests with an upstream digest check it on hits and fresh responses, refetching a failing hit, but CurseForge responses with uncorrelatable exact matches or omitted file IDs are skipped; other matches stay usable.

The client owns its HTTP client, policy, and logger; command composition supplies the disk root. Indexes initialize lazily. Invocations share cached objects but not transport or provider configuration. Caller context covers cache-hit reads and copies. The configured TTL applies without an override; closing drains active operations and leaves unused stores unopened.

## Index persistence

A process keeps the index in memory. A read stats the published snapshot and its append log and reloads only when their identity changed, so a cache hit takes no file lock. A committed response or removal appends one record under the cache file lock; the log is replayed on load and compacted into an atomically replaced snapshot at a bounded size. Multi-process visibility is preserved: a writer publishes its record before releasing the lock, and a reader notices the changed file identity and reloads it. A torn record tail is discarded, so a crash costs at most the entries that were not published.

## Publication and verification

A download is staged while its content digest and any supplied upstream integrity expectation are checked. On a cache hit, bytes are copied from the indexed object; installation then verifies the materialized artifact against the hashes recorded in the lock. A corrupt or unreadable cached object can be treated as a miss during an online download.

An active staging writer holds a lease on its staging files until commit or abort, so cleanup cannot reclaim an active write.

Installation writes verified artifacts to the per-user artifact store, a content-addressed store outside every workspace. Objects are addressed by SHA-256 only, independent of any consumer filename. A lock hits the store without contacting the network or cache; a miss copies verified bytes from the network cache or the network into the store. Verification always checks every digest the artifact declares, including SHA-256, so a corrupt store object is replaced rather than reused. In offline mode lucy uses a store hit or a suitable network-cache entry without fetching; an absent object in both cannot supply the bytes.

## Separate stores

The network cache, the per-user artifact store, and each workspace's tracked-file store all use content-addressed storage but have different owners and retention rules. The network cache index represents reusable request results and expires them. The artifact store retains installed artifacts across cache clearing, and a registered server's lock keeps the objects it pins. `.lucy/objects/sha256/` contains captured working-file contents referenced by declarations, history, and pending transactions. Clearing the network cache leaves tracked-file history, the artifact store, and a server's working files in place.

`lucy store list` shows every stored object. `lucy store gc` removes objects no registered server's lock references. It takes the operation gate, workspace writer locks, and the registry mutation lock, reads references, then the content store lock to sweep. A missing, unreadable, or unknowable reference set fails before any deletion. Holding the gate from lease check to last removal blocks artifact acquisition between reference read and deletion.

The operation gate and leases occupy a private operations directory apart from the content store's staging namespace. Concurrent artifact operations and collection must share one Lucy version. Each store owns its layout; consumers take object paths from the store, never rebuilding digest paths.

An operation takes the artifact-store lease before its workspace writer lock and first artifact access. Planning holds both only while resolving; its plan carries fingerprints and a resolved lock and treats materialized objects as apply-time work, so collection may remove them after planning. Applying reacquires the lease, rechecks fingerprints, and materializes any missing object.

An object digest identifies content; proving upstream provenance needs the verified lock hash. That hash ties expected bytes to an artifact record, while cache integrity metadata records what was checked when the response was acquired.
