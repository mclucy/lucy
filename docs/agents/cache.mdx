---
title: "Network cache and content storage"
description: "Request indexing, artifact verification, expiration, and distinct object-store lifecycles"
---

`cache` stores reusable network responses separately from a workspace. Its index maps a canonical request key to an entry with a content digest, filename, kind, integrity metadata, size, and expiration. The bytes live in a `cas.Store` addressed by SHA-256. Several request keys can refer to the same object; an object is reclaimed only when no retained index entry references it.

Metadata and artifacts have separate policy limits and lifetimes. The default metadata refresh period is four hours and the artifact retention period is seven days; request-specific metadata can choose a different TTL. Expiration affects whether an indexed response can be reused, not the meaning of a lock or receipt. Non-success HTTP responses are not stored as successful metadata responses.

`cache.Client` owns its HTTP client, policy, and diagnostic logger. Command composition supplies the disk root explicitly. Each instance initializes its index lazily; separate invocations can share cached objects without sharing transport or provider configuration. Metadata and artifact requests receive the caller's context, including cache-hit reads and copies. Configured TTL policy governs requests without an explicit override. `Close` waits for cache operations and releases an opened store without initializing an unused one.

## Publication and verification

A download is staged while its content digest and any supplied upstream integrity expectation are checked. Failed integrity checks do not publish the new destination or cache entry. On a cache hit, bytes are copied from the indexed object; installation then verifies the materialized artifact against the hashes recorded in the lock. A corrupt or unreadable cached object can be treated as a miss during an online download.

Installation writes verified artifacts to the per-user artifact store, a `cas.Store` outside every workspace. Objects are addressed by SHA-256 only and carry no consumer filename. A lock hits the store without contacting the network or cache; a miss copies verified bytes from the network cache or the network into the store. Verification always checks every digest the artifact declares, including SHA-256, so a corrupt store object is replaced rather than reused. In offline mode Lucy uses a store hit or a suitable network-cache entry without fetching; an absent object in both cannot supply the bytes.

## Separate stores

The network cache, the per-user artifact store, and each workspace's tracked-file store all use content-addressed storage but have different owners and retention rules. The network cache index represents reusable request results and expires them. The artifact store retains installed artifacts across cache clearing, and a registered server's lock keeps the objects it pins. `.lucy/objects/sha256/` contains captured working-file contents referenced by declarations, history, and pending transactions. Clearing the network cache does not clear tracked-file history, the artifact store, or a server's working files.

`lucy store list` shows every stored object. `lucy store gc` removes objects that no registered server's lock references. It takes the operation gate, every registered workspace's writer lock, and the registry mutation lock, then collects references before taking the content store lock for the sweep. A missing, unreadable, or unknowable reference set makes the command fail before deleting anything. Collection holds the operation gate from its lease check through the last removal, so an operation that acquires an artifact-store lease cannot acquire artifacts between the reference read and deletion.

An operation acquires the artifact-store lease before its workspace writer lock and before its first artifact access. `PlanInstall` holds the lease and the writer lock only while it resolves; the plan it returns carries fingerprints and a resolved lock, not a reservation on the objects resolution materialized, so collection may remove them once planning returns. `ApplyPlan` acquires the lease again, rechecks the fingerprints, and materializes any object the store no longer holds.

An object digest identifies content; it does not by itself assert upstream provenance. A verified lock hash ties expected bytes to an artifact record, while cache integrity metadata records what was checked when the response was acquired.
