---
title: "Java runtime architecture"
description: "Requirements, runtime selection, and provisioning for a locked server"
---

Lucy separates the Java requirement of a server from the runtime available on a particular machine. The lock records Mojang's advisory and the manifest's optional version and distribution overrides. Java dependencies declared by enabled package modules remain on those modules; requirement evaluation combines them when evaluating a lock. A local `java.home` selects an installation and stays outside portable server intent.

## Requirement construction

The advisory is treated as a minimum major version. A manifest version pin is an exact major version, and a named distribution requires that specific distribution. Required and incompatible Java constraints from enabled modules are interpreted using the descriptor's version dialect and become runtime constraints; other Java dependency kinds stay outside that set. An unparseable constraint is ignored for Java selection and logged at debug level.

Requirement evaluation searches for the lowest major version satisfying all constraints. The provisioning target is the pinned major when present, otherwise the lowest satisfying major, or the advisory if no major satisfies all constraints. A conflict is reported as a problem and leaves Java compatibility advisory. A bootstrap step that requires a Java executable fails when none is usable.

## Selecting an installed runtime

Configured Java home merges the global and workspace values. A present workspace value masks the global one, including an explicit empty value. Relative paths are resolved against their configuration scope. A non-empty selection is probed and honored without fallback, even when it falls short of the requirement; an unusable selection produces a problem and leaves selection empty.

Without a configured home, toolchain discovery locates installed runtimes and runtime selection ranks them by the number of unmet conditions. Ties prefer a runtime meeting the advisory, then the oldest major, then the newest update. A named distribution requires a build bearing that brand; unbranded builds fall outside it. Selection produces a check record containing the chosen runtime, its source, and problems; the check records evidence about this machine, while lock pins come from resolution.

Runtime selection discovers Java runtimes only. It never runs a compiler or Gradle, which belong to the build discovery of the compilation command. Discovery is memoized for the process, so a command that selects more than once probes each candidate at most once, and it records probe results in the per-user cache. An entry is reused only while the resolved Java executable, the `release` file of its installation home, and the `JAVA_HOME` value that selected it keep their recorded identities; any mismatch probes again. A missing, unreadable, or corrupt cache file is ignored and rewritten, and an entry whose executable is gone is pruned. A missing cache costs probes, never correctness.

## Provisioning boundary

Before staging, the installer selects a runtime and may call the provisioning callback supplied by the command layer. After successful provisioning it repeats selection; prompt presentation belongs to the command layer. A configured home remains authoritative.

Java provisioning builds candidate plans from detected version managers, system package managers, optional vendor repositories, and a direct-download fallback. Plans are ranked toward managers already owning a local Java, then other user managers, system managers, repository additions, and downloads. Host interactivity, elevation availability, and repository consent can make a plan unavailable. Download plans require a verifiable SHA-256 checksum.

Provisioning operates through an invocation-scoped host that owns process execution and discovers environment and platform facts directly. Relevant host probes are lazy and cached only within that host instance. Planning captures the managed destination so displayed commands and execution use the same Java home. Consent and interactivity remain per-operation policy rather than mutable host facts. A managed installation returns its Java home to post-provision selection, including when the home lies outside the default managed directory.

On Linux, system package plans preserve the previous `java` alternative when it can be observed. Cancellation interrupts the installer and waits for it before restoring; an installer that ignores the interrupt can delay exit, and lucy skips restoration when confirmation that the child stopped is unavailable. This relies on sudo waiting for its command or a directly run package manager cleaning up its own children; daemonized children are outside that guarantee. Restoration has its own timeout, and its failure is returned with the install error.

Gradle compilation has a separate JVM and compiler selection process: see [Compilation architecture](/agents/compilation). Server runtime selection applies to the locked server, while the JDK that runs or compiles a Gradle build comes from Gradle's own selection.
