---
title: "Telemetry client"
description: "Local collection state, invocation contexts, bounded outbox delivery, and diagnostic report rules"
---

`telemetry` is a self-contained client. It owns identity, policy, counters, an on-disk outbox, and HTTP transport to the ingestion service. It does not know about commands, workspaces, or terminal output. `cmd/cmd_telemetry.go` owns the invocation lifecycle: it builds the client, collects contexts while the command runs, records the terminal event, assembles diagnostic reports, and presents everything through the ordinary command output path. Collection failure never changes a command's exit status.

## Local state

The state directory is `telemetry` under the platform user-data root: `LOCALAPPDATA/lucy`, `~/Library/Application Support/lucy`, or `$XDG_DATA_HOME/lucy` with `~/.local/share` as the fallback. It holds `state.json` (identity, policy, counters, and the outbox index), `queue/<id>.json` (one record payload per file), `state.lock`, and `.alpha_telemety_notice_shown` (the one-time notice claim). Directories are `0700` and files `0600`.

`ClaimNotice` creates the marker with exclusive creation and reports whether this process won the claim. `cmd` claims before it renders the notice, so one invocation presents the notice per machine; a claim that fails to render stays claimed. A disabled client never claims, so the notice stays available until telemetry is on.

`state.json` is the single source of truth. Accepting a record writes its payload file first, then replaces `state.json` atomically, so a record is queued and counted in one step. Files are encoded deterministically; readers reject an unknown schema version, an invalid policy, or a malformed identity as corrupt, and further mutation is refused until `lucy telemetry off` rewrites the state. Queue pruning and orphan removal keep payload files consistent with the index when a replacement is interrupted.

Every mutation runs under two locks: an in-process semaphore and a file lock, so concurrent Lucy invocations serialize. Each operation passes one wait budget to both layers. Reads and submissions allow 2 s, enqueue caps its share at 250 ms, flush tries once and reports a busy skip, and explicit enable, disable, and identity actions wait until their context ends.

## Policy and identity

The effective decision is: local development builds disable collection and uploads regardless of stored policy; otherwise `LUCY_TELEMETRY` with a false-like value disables collection; otherwise an explicit `opt_in` or `opt_out` wins; otherwise the channel default applies, which is on for alpha and beta. A disabled client reports a skip reason and writes no records.

The installation UUID is created lazily by the first record or by the first `telemetry on`. Read-only commands still create one when they queue an event; this is not an opt-out. `reset-id` rotates the UUID and starts a new statistics window; queued records keep their original IDs and payloads, and remote data is untouched. Runtime uploads count in the new window. `off` marks the state `purge_pending`, deletes the queue directory, and clears the index; the marker makes an interrupted purge complete on the next read.

## Invocation events and contexts

An event carries invocation ID, identity, occurrence time, command path without the `lucy ` prefix, build version and commit, channel, OS, architecture, duration, outcome, error code, schema version, effective policy, and up to 16 contexts. Contexts come from subsystems that already observed the data: `workspace` and `java` are recorded by `internal/cli` only when observation happened, and `agent` records whether an agent tool was detected. `present`, `absent`, and `failed` distinguish a missing installation from a failed observation. Context data is bounded at 8 KiB per context. Telemetry never triggers discovery, network probes, or workspace reads of its own.

Outcome classification is a CLI-boundary decision: cancellation and deadline become `canceled`, usage errors become `invalid_invocation`, panics and handled exit errors become `failure` with a diagnostic report. Silent exits record an event without a report. `lucy telemetry*`, `lucy agent-report`, and shell-completion commands do not record invocation events.

## Reports

Reports have three kinds: `failure`, `panic`, and `agent_feedback` (from `lucy agent-report`). The body is assembled from allowlisted sources only: command path, error category, captured stage messages (capped at 128, allowlisted strings), and the Lucy frames of a panic stack (capped at 32). Free text is normalized to printable UTF-8, then stripped of ANSI and control bytes, credentials and authorization headers, private keys, common provider tokens, URLs with embedded userinfo, IPv4/IPv6 literals, and Unix, home, Windows, and UNC paths. Over-long bodies are truncated with a marker and the record is fitted to the 64 KiB event and report bounds.

## Outbox and delivery

Flush runs once at the end of an invocation that performed work. Guidance-only exits record their event but skip the flush: `--help` for any command, `lucy help`, a version request, and a command group invoked without a subcommand (`lucy java`, `lucy file`, and their peers). Reading help therefore never sends traffic; those records wait for the next invocation that performs work.

Enqueue prunes expired records (older than 7 days) and then the oldest records until both bounds hold: 512 records and 4 MiB. A single record larger than the queue budget is refused. The just-enqueued record survives unless it is the one that exceeds the bound, in which case its payload file is removed.

Flush prunes, skips an empty queue, honours a cooldown window, checks `GET /health` with a 2 s budget, clears the cooldown on success, and then uploads at most four batches. Each batch contains up to 50 records within 256 KiB, oldest first; unreadable payload files are dropped locally so they cannot block healthy records. Requests use a 5 s timeout and up to three attempts with 250 ms backoff. Transport failures set a 10-minute cooldown and persist the last error. Flush caps the caller's context at 15 s; the CLI passes 2 s, so a slow service leaves records queued rather than delaying the command.

Responses classify records individually. Accepted and rejected IDs are removed and counted; an unacknowledged record stays queued. A batch-level rejection (`batch_invalid`) drops the batch as rejected instead of retrying it. The index remembers the last 2048 accepted IDs so a retried request cannot double-count after a lost response. Records still pending after four batches remain for a later invocation.

## Failure and recovery

The outbox is the recovery mechanism: any failure before a record is accepted leaves it on disk, and the next enabled invocation retries within the prune window. Errors from enqueue, flush, and report submission are reported through the CLI's normal error path only for explicit telemetry actions; during normal commands they are logged and ignored. `--offline` suppresses the flush but still queues. A command that never reaches the boundary (SIGKILL) leaves no event; a panic that reaches the boundary still produces an event and a report.
