---
title: "Telemetry client"
description: "Local collection state, invocation contexts, bounded outbox delivery, and diagnostic report rules"
---

Lucy's telemetry subsystem is a self-contained client. It owns identity, policy, counters, an on-disk outbox, and HTTP transport to the ingestion service. The command entry point manages the invocation lifecycle: it initializes the client and records the terminal event. The CLI collects invocation contexts, formats diagnostic reports, and renders user-facing telemetry output. Collection failure never changes a command's exit status.

## Local state

The state directory is `telemetry` under the platform user-data root: `LOCALAPPDATA/lucy`, `~/Library/Application Support/lucy`, or `$XDG_DATA_HOME/lucy` with `~/.local/share` as the fallback. It holds `state.json` (identity, policy, counters, and the outbox index), `queue/<id>.json` (one record payload per file), `state.lock`, and `.alpha_telemety_notice_shown` (the one-time notice claim). Directories are `0700` and files `0600`.

The notice claim creates the marker with exclusive creation and reports whether this process won the claim. The CLI claims before it renders the notice, so one invocation presents the notice per machine; a claim that fails to render stays claimed. Only an enabled client claims, so the notice stays available until telemetry is on.

`state.json` is the single source of truth. Accepting a record writes its payload file first, then replaces `state.json` atomically, so a record is queued and counted in one step. Files are encoded deterministically; readers reject an unknown schema version, an invalid policy, or a malformed identity as corrupt, and further mutation is refused until `lucy telemetry off` rewrites the state. Queue pruning and orphan removal keep payload files consistent with the index when a replacement is interrupted.

Every mutation runs under two locks: an in-process semaphore and a file lock, so concurrent lucy invocations serialize. Each operation passes one wait budget to both layers. Reads and submissions allow 2 s, enqueue caps its share at 250 ms, flush tries once and reports a busy skip, and explicit enable, disable, and identity actions wait until their context ends.

## Policy and identity

The effective decision is: local development builds disable collection and uploads regardless of stored policy; otherwise `LUCY_TELEMETRY` with a false-like value disables collection; otherwise an explicit `opt_in` or `opt_out` wins; otherwise the channel default applies, which is on for alpha and beta. A disabled client reports a skip reason and writes no records.

The installation UUID is created lazily by the first record or by the first `telemetry on`. Read-only commands still create one when they queue an event; this is not an opt-out. `reset-id` rotates the UUID and starts a new statistics window; queued records keep their original IDs and payloads, and remote data is untouched. Runtime uploads count in the new window. `off` marks the state `purge_pending`, deletes the queue directory, and clears the index; the marker makes an interrupted purge complete on the next read.

## Invocation events and contexts

An event carries invocation ID, identity, occurrence time, command path without the `lucy ` prefix, build version and commit, channel, OS, architecture, duration, outcome, error code, schema version, effective policy, and up to 16 contexts. `duration_ms` appears only when the invocation measured it; a present zero is a real measurement. The client has no cross-process session identifier: `invocation_id` identifies one event and joins its automatic failure or panic report and local log. Context data is bounded at 8 KiB per context. Contexts come only from state a command already observed. Telemetry never triggers discovery, network probes, or workspace reads of its own, and it does not scan the filesystem to fill a context.

Every context has `type`, `status`, optional `version`, optional `reason`, and optional `data`. New clients write `version` 1 on every context they emit; context rows written before this change can lack `version` and `reason`. A `present` context carries `data`. An `absent` context carries no data and explains itself with `not_observed`, `not_reached`, `not_applicable`, or `no_result`. A `failed` context carries no data and the reason `observation_failed`. The reason describes the missing observation, not the command's failure. A count that is absent from `data` is unknown, not zero.

The existing types keep their shapes. `workspace` carries product, product version, Minecraft version, and package count; a missing installation is `absent`, and a selection error is `failed`. `java` carries major, version, and distribution when a runtime is selected; a check that finds no runtime is `absent`, and a failed check is `failed`. `agent` records whether an agent tool was detected.

New types describe one invocation:

| Type | `data` when present |
|---|---|
| `invocation` | `intent` (`command` or `invalid_usage`), `output` (`text`, `json`, or `json_compact`), `offline`, optional `flags` as `{name, kind}` objects, optional `positionals` count |
| `execution` | `slow`, plus optional `phases`, `active_phase`, `cancel_reason`, `failure_kind`, `http_ms`, and `lock_ms` |
| `prompt` | `mode`, `count`, `wait_ms`, `aborted`, and optional `interrupted` |
| `scale` | any observed subset of `packages`, `requested_packages`, `files`, `completed_files`, and `candidates` |
| `warnings` | `recoverable`, plus `resolution_rejections` where observed |
| `collection` | `local_log` |

`invocation.flags` records names and value kinds only. Allowed names are `offline`, `json`, `json-compact`, `no-interactive`, `no-style`, `no-color`, `server`, `core`, `core-version`, `minecraft`, `locked`, `yes`, `interactive`, `dry-run`, `all`, `provider`, `source`, `loader`, `latest`, `version`, `channel`, `force`, `output`, `path`, `directory`, `name`, `package`, `java`, `log-file`, `log-level`, and `print-logs`. `kind` is `boolean`, `number`, `selector`, `version`, `text`, or `list`. A flag outside the list is omitted. The client reads a value only when its effective boolean is itself a recorded field: offline mode, output mode, and prompt mode. Raw arguments and flag tokens are never retained. `positionals` is the number of positional arguments, capped at 10000.

`execution.phases` holds at most 24 entries of `{name, elapsed_ms, state}`. `state` is `complete` or `active`; `active` means the phase had not finished when the event was recorded. Phase names are limited to `setup`, `command`, `server`, `packages`, `install`, `python_environment`, `download_pack`, `download_archive`, `files`, `loader_installer`, `adoption`, and `identification`. A parent phase and its subphases can overlap, so the entries are not exclusive durations and must not be summed as total elapsed time. `elapsed_ms` is capped at 604800000. `active_phase` names the unfinished phase. `cancel_reason` is `prompt_aborted`, `interrupted`, `deadline`, or `context_canceled`. `failure_kind` is `usage`, `panic`, `handled`, or `command`. `http_ms` and `lock_ms` are optional cumulative milliseconds spent waiting for HTTP response headers through the service cache and for file-lock acquisition through the workspace writer and cache index; the samples can overlap each other and the phases, and they are not added to `elapsed_ms`. `slow` is true when the invocation ran for at least 30 seconds; it does not mean the run failed.

`prompt.count` and `prompt.wait_ms` describe prompts the command opened. `mode` is `available`, `non_interactive`, `no_terminal`, or `unknown`. `count` is capped at 10000. `wait_ms` is the cumulative observed time prompts were open, capped at 604800000, and is not a share of the command's elapsed time. `aborted` means the user explicitly aborted the form. `interrupted` means the surrounding context was canceled while a form was open, and is omitted when false. An abort is not an external cancellation. Neither marker records typed input or the abort reason.

`scale` values are integers from 0 to 1000000, and each key appears only when the command already computed it. `warnings.recoverable` counts recoverable warnings presented or collected during the run, capped at 10000; `resolution_rejections` appears only when the resolver observed rejected candidates. `collection.local_log` says whether the invocation ID is available in a local diagnostic log, not whether the log was uploaded. The log body, its path, and its contents stay local.

Context version 1 is the wire schema described here. The writer stamps it on every context, including the existing `workspace`, `java`, and `agent` types, whose data shapes do not change. Readers treat a missing version as an older row.

Outcome classification is a CLI-boundary decision: cancellation and deadline become `canceled`; usage errors become `failure` with `usage.invalid_invocation` and invocation intent `invalid_usage`; panics and handled exit errors become `failure` with a diagnostic report. Silent exits record an event without a report. The client treats the offending token as opaque, regardless of whether the error came from a typo, a deliberate test, or a script probe. Invocation policy suppresses automatic collection and upload for telemetry controls, agent reports, generated help and shell integration commands, and successful guidance-only invocations. An explicit `agent-report` can still submit a report and flush the outbox. Failed guidance invocations remain observable.

## Reports

Reports have three kinds: `failure`, `panic`, and `agent_feedback` (from `lucy agent-report`). The failure body is one line of JSON assembled at the command boundary: `command`, `code`, `message`, `stages`, `stack`, and `facts`. `message` is the error text with consecutive duplicate lines collapsed, capped at 512 bytes. `stages` holds each captured stage message with its repetition count rather than one entry per retry. `stack` holds the lucy frames of a panic, capped at 32.

`facts` is the same evidence the machine-readable error document carries, projected from the typed error chain. A resolution failure contributes its project, provider, project ID, ecosystem, Minecraft version, candidate count, aborted flag, and rejection groups. A rejection group about a module requirement also carries `required_by`, `dependency`, `constraint`, and `selected`, and a requirement the server itself fails arrives with kind `server` first, because no candidate choice can satisfy it. Search-limit exhaustion contributes its attempt count; identical failures collapse into one entry with an occurrence count, and the chain lists the typed errors on the way to the root cause, including joined children. Facts carry identifiers, enum names, counts, and the module-requirement detail the resolver formats from catalogue data — never log fields or free-form state. The whole body is then normalized to printable UTF-8, stripped of ANSI and control bytes, credentials and authorization headers, private keys, common provider tokens, URLs with embedded userinfo, IPv4/IPv6 literals, and Unix, home, Windows, and UNC paths. Over-long bodies are truncated with a marker and the record is fitted to the 64 KiB event and report bounds.

Report metadata and bodies are private and retained for 14 days; events and their contexts are retained for 30 days. A context states whether an observation happened and stays bounded; it never contains the report body, and `collection.local_log` does not turn the local log into an uploaded record. Automatic reports accompany failures and panics; successful and canceled commands keep their detailed timings in the execution context. An explicit `lucy agent-report` submission can queue an `agent_feedback` body.

## Outbox and delivery

Flush runs once at the end of an invocation that performed work. Successful guidance-only exits, including `--help`, version requests, and command groups invoked without a subcommand, skip event enqueue and outbox flush.

Enqueue prunes expired records (older than 7 days) and then the oldest records until both bounds hold: 512 records and 4 MiB. A single record larger than the queue budget is refused. The just-enqueued record survives unless it is the one that exceeds the bound, in which case its payload file is removed.

The uploader runs only when telemetry is enabled and a binding exists. It checks `GET /health` with a 2-second budget, clears cooldown on success, and uploads bounded batches of complete queued events. Non-canceled health-check failures and upload failures, except invalid-batch rejections, set a 10-minute cooldown and persist the last error.

Responses classify records individually. Accepted and rejected IDs are removed and counted; an unacknowledged record stays queued. A batch-level rejection (`batch_invalid`) drops the batch as rejected instead of retrying it. The index remembers the last 2048 accepted IDs to keep a retried request from double-counting after a lost response. Records still pending after four batches remain for a later invocation.

An event upload attempt can carry an optional `upload` envelope with `queue_ms`, `attempts`, and `throttles`. The ingestion worker validates it and stores a `transport` context on the event; the client never writes that context. The record digest excludes the envelope, so retries with changed values resolve to the same event. `queue_ms` measures the wait from enqueue to that attempt alone; the full `occurred_at` to `received_at` interval describes a different span.

## Failure and recovery

The outbox is the recovery mechanism: any failure before a record is accepted leaves it on disk, and the next enabled invocation retries within the prune window. Errors from enqueue, flush, and report submission are reported through the CLI's normal error path only for explicit telemetry actions; during normal commands they are logged and ignored. `--offline` suppresses the flush but still queues. A command that never reaches the boundary (SIGKILL) leaves no event; a panic that reaches the boundary still produces an event and a report.
