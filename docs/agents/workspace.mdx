## Discovery and selection

Installation discovery scans a server directory and reconciles recognizer results into installations. An installation has an identity and a collection of members with roles such as entry point or payload. A server JAR used as another installation's payload is not necessarily an independent server. Equivalent identities and overlapping claims are reconciled before selection; diagnostics retain conflicts and unreadable or unknown artifacts.

Discovery and selection are separate. Discovery does not choose a runtime or read workspace declarations. Selection uses a directly chosen installation when supplied, otherwise an identity expectation, otherwise a persisted declaration, otherwise an inference policy. Entry-point members prove launchability but never become the selection result. A missing declared installation and an ambiguous selection are distinct outcomes; neither proves that the directory has no server files.

Workspace observation assembles local observations of installations, environment wrappers, declarations, and package files. Reselection refreshes package observations; upstream identification must be repeated afterward.

Package descriptors provide local module metadata. Observation keeps one entry per readable descriptor, so a jar carrying several loaders yields several entries. Adoption claims one package per file under the ecosystem the server loads. Every file left unmanaged is reported with its reason: client-only, unreadable descriptor, an ecosystem the server does not load, or no upstream identity.

## Tracked-file state

A tracked-file declaration contains a workspace-relative path, optional accepted SHA-256 digest, change policy, and optional recovery URL. It describes accepted intent, not the current bytes. The lock carries the declared files; current observations and deviation warnings are computed separately.

Working-file tracking stores captured bytes in the workspace-local `.lucy/objects/sha256/` content-addressed store and appends events to `.lucy/history/files.jsonl`. History distinguishes an event sequence from the accepted revision activated by that event. An accepted revision has a parent, so reverting follows that revision chain rather than toggling between the last two events. Captured working bytes can exist without being an accepted revision.

Tracked-file mutations share the workspace writer lock. Their journal, `.lucy/file-commit.json`, records before and after images and the intended history event. Recovery uses history to choose an image and refuses to overwrite an unrelated edit. [Installation](/agents/resolution) has a separate journal and recovery path. Read-only file history refuses an unfinished transaction.

Tracked files and runtime-owned outputs are different ownership domains. Installation checks for destination conflicts, preserves existing tracked working files, and can provision missing accepted content from a verified local object or recovery URL. A hash in a declaration is an identity for bytes, not a transfer of those bytes.
