## Discovery and selection

Installation discovery scans a server directory and reconciles recognizer results into installations. An installation has an identity and a collection of members with roles such as entry point or payload. A server JAR used as another installation's payload is not necessarily an independent server. Equivalent identities and overlapping claims are reconciled before selection; diagnostics retain conflicts and unreadable or unknown artifacts.

Discovery and selection are separate. Selection owns runtime choice and workspace declarations: it uses a directly chosen installation when supplied, otherwise an identity expectation, otherwise a persisted declaration, otherwise the installation whose recognized entry points, payloads, and libraries account for strictly more files than any other candidate's, otherwise an inference policy. Configuration files do not take part in that comparison. Lucy uses the strict majority and warns `multiple server runtimes found; using X automatically`, naming the other runtimes and the `lucy init --core <product>` command that selects one; a tie stays ambiguous. Entry-point members prove launchability but never become the selection result. A missing declared installation and an ambiguous selection are distinct outcomes; neither proves that the directory has no server files.

Workspace observation assembles local observations of installations, environment wrappers, declarations, and package files. Reselection refreshes package observations; upstream identification must be repeated afterward.

Package descriptors provide local module metadata. Observation keeps distinct paths when two JARs declare one identity. Adoption selects one descriptor per file; a file stays unmanaged when descriptors conflict, are client-only or unreadable, name an ecosystem the server does not load, or have no upstream identity.

## Tracked-file state

A tracked-file declaration contains a workspace-relative path, optional accepted SHA-256 digest, change policy, and optional recovery URL. It describes accepted intent, not the current bytes. The lock carries the declared files; current observations and deviation warnings are computed separately.

Working-file tracking stores captured bytes in the workspace-local `.lucy/objects/sha256/` content-addressed store and appends events to `.lucy/history/files.jsonl`. History distinguishes an event sequence from the accepted revision activated by that event. An accepted revision has a parent, so reverting follows that revision chain rather than toggling between the last two events. Captured working bytes can exist without being an accepted revision.

Tracked-file mutations share the workspace writer lock. Their journal, `.lucy/file-commit.json`, records before and after images and the intended history event. Recovery uses history to choose an image and refuses to overwrite an unrelated edit. [Installation](/agents/resolution) has a separate journal and recovery path. Read-only file history refuses an unfinished transaction.

Tracked files and runtime-owned outputs are different ownership domains. Tracked files take precedence: installation preserves existing tracked working files and can provision missing accepted content from a verified local object or recovery URL. A hash in a declaration is an identity for bytes, not a transfer of those bytes.

## Runtime ownership and displacement

Runtime outputs are the files a bootstrap method produces: server jars, `libraries/`, `versions/`, `cache/`, launchers, and run scripts. They are owned as the runtime image of the lock's recipe; `--overwrite` governs package destinations, and runtime outputs never need it. At commit, an unowned runtime output with identical bytes is claimed without a rewrite. A runtime output with other bytes is replaced, and its before-image is kept under `.lucy/displaced/<transaction-id>/files/<path>` with an `index.yaml` that records path, SHA-256, and mode. The journal entry carries the displacement flag. Displacement materializes only after the commit point: recovery before it restores the before-images, and recovery after it completes the cleanup. Lucy never deletes displaced content; the workspace owner does.

Initialization owns matching managed files from the locked recipe's runtime image, or only digest-pinned files when the image is unavailable, without writing runtime files.

## Store link mode

`store.link` selects how stored content reaches an installed file. `clone` (the default) uses a copy-on-write clone where the filesystem supports it and a plain copy otherwise. `hardlink` links the stored inode and deploys the file without write bits, so an in-place rewrite fails instead of changing the shared copy. A file whose mode cannot match the stored copy, such as an executable launch script, is cloned. A hardlink applies only when the store and the destination share one filesystem; otherwise Lucy clones or copies. On Windows, Lucy cannot share a stored inode, so `hardlink` installs plain copies and keeps their write bits.
