---
title: "Server bootstrap architecture"
description: "How locked server products become launchable files"
---

A server product is not always a single runnable JAR. Resolution records a product, Minecraft and core versions, a core artifact, a bootstrap method, and supporting inputs in the locked server. The manifest has no bootstrap field; resolution selects the method from the product. An input is a Maven library or a Mojang artifact. The lock does not record input placement; the bootstrap method decides the placement. These are server bootstrap inputs, not mod or plugin requirements.

Product resolution inspects upstream metadata to construct this locked definition, analyzing installer archives or Paperclip bundles prior to installation. For example, Paperclip download context identifies the expected Mojang server JAR and its SHA-256 hash, allowing verification that the bundle targets the requested Minecraft version. Forge-family installer metadata describes required libraries and execution processors. Resolution fails when a profile library declares a download path that differs from the Maven path of its coordinate. Locking these inputs allows staging to operate deterministically from selected artifacts instead of discovering a new product version while staging.

## Bootstrap methods

Server preparation operates in an installation staging tree. It copies or extracts locked inputs under the server directory, then dispatches on the bootstrap method in the lock:

| Method | Preparation |
| --- | --- |
| `vanilla` | Copy the core artifact as `server.jar`. |
| `paperclip` | Copy the core as `server.jar` and run Paperclip in patch-only mode. |
| `fabric` | Place the loader in the library layout and generate launch scripts, a launcher shim, and launcher properties from the locked classpath. |
| `quilt` | Place the loader in the library layout and generate the Quilt launcher JAR and launcher properties from the locked classpath. |
| `forge` | Read the Forge or NeoForge installer's server profile and run its processors with the locked inputs. Both products share the installer profile format. |

An empty or unknown method is invalid, and Lucy tells the user to resolve the server again.

`InputPath` returns the placement of each input from the method: Maven libraries go to `libraries/<maven path>`; the Mojang server jar goes to `server.jar`, except Paperclip reads it from `cache/mojang_<minecraft>.jar`; server mappings go to `server-mappings.txt`. A Forge installer can carry libraries in itself; such an input names the embedded entry, and the installer digest addresses it.

Paperclip and Forge installer processors execute Java when there is no reusable snapshot. Processor outputs with expected hashes are checked. Fabric and Quilt generate launchers from their locked classpaths.

A bootstrap snapshot records checked runtime files and seeds. Its recipe key is the hash of the Lucy build identity, the bootstrap method, the product, the Minecraft and core versions, the core digest, and each input identity and digest in lock order. Input order is part of the key because Fabric and Quilt derive the launcher classpath from it. The Lucy build identity is the SHA-256 of the running executable, so a new Lucy build rebuilds snapshots and makes the bootstrap fingerprint of existing receipts stale; the next install restages the runtime. A receipt's bootstrap fingerprint combines this recipe key with the locked server directory, so snapshots stay shareable across directories while moving the server directory restages its runtime. A restore compares every restored file with the snapshot entries by SHA-256; for a managed file it also compares the read and execute permission bits. Install and adoption rebuild from the locked inputs when a snapshot fails to restore, and drop a snapshot that fails this comparison. A failure to store a fresh build logs a warning. Adopted user trees never populate the snapshot cache.

A fresh bootstrap is accepted when every file the method wrote is a declared output; an undeclared file fails the installation.

Subprocess output streams to terminal progress and a per-command log under `installer` in the platform log directory. Each command's header is recorded even when it prints nothing, and both stdout and stderr reach the file. The log is bounded to 64 MiB and discarded on success; a failure keeps it and names its path and size. Truncation or a write failure is reported.

Initialization compares existing runtime files with the locked recipe's snapshot or a new offline build in a private stage.

Bootstrap methods also define the launch command, MCDReforged log handlers, output paths, and superseded core metadata that other subsystems require. Installation and workspace observation consume these unified descriptions.

An upstream installer that an archive carries is identified from its contents, never its name: a Forge or NeoForge `install_profile.json` supplies the product, loader and Minecraft versions, whether it keeps that declaration at the top level or, as installers predating the install profile spec do, nests it under `install`; a Fabric or Quilt manifest main class supplies the product. Forge and NeoForge installers run natively with `--installServer` in the target root; this produces the same layout their installer produces outside Lucy. Import uses this before initialization, so the prepared tree is adopted rather than locked first. The run creates no lock or receipt; ownership begins only when initialization commits.

Bootstrap output becomes subject to installation's ownership and commit checks. The bootstrap stage does not by itself publish a workspace receipt or authorize removal of unrelated files. Runtime discovery later recognizes installations from their actual members.

Install treats the runtime as current when the receipt's bootstrap fingerprint equals the lock's installation key, the snapshot recipe key plus the server directory, and every runtime file the receipt owns still matches its recorded digest. The receipt also records the seed paths the bootstrap produced: a recorded seed that is absent or not a regular file makes the runtime stale and the next install restages it, while an edited seed stays user-owned. Seed, discard, and bootstrap-only files need no ownership entry.
