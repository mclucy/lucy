---
title: "Server bootstrap architecture"
description: "How locked server products become launchable files"
---

A server product is not always a single runnable JAR. Resolution records a product, Minecraft and core versions, a core artifact, a bootstrapper, and supporting inputs in the locked server. An input has a destination path and either its own artifact metadata or a reference to content embedded in the installer. These are server bootstrap inputs, not mod or plugin requirements.

Product resolution inspects upstream metadata to construct this locked definition, analyzing installer archives or Paperclip bundles prior to installation. For example, Paperclip download context identifies the expected vanilla Mojang JAR and its SHA-256 hash, allowing verification that the bundle targets the requested Minecraft version. Forge-family installer metadata describes required libraries and execution processors. Locking these inputs allows staging to operate deterministically from selected artifacts instead of discovering a new product version while staging.

## Preparation adapters

Server preparation operates in an installation staging tree. It copies or extracts locked inputs under the server directory, then dispatches on the declared bootstrap method:

| Bootstrapper | Preparation |
| --- | --- |
| Empty | Copy the core artifact as `server.jar`. |
| `paperclip` | Copy the core as `server.jar` and run Paperclip in patch-only mode. |
| `fabric` | Place the loader in the library layout and generate launch scripts, a launcher shim, and launcher properties from the locked classpath. |
| `forge-installer` | Read the installer's server profile and execute its processors using the locked inputs. |

Paperclip and installer processors execute Java during staging. A missing Java runtime is therefore a bootstrap error even though a Java version mismatch alone is a warning. Processor outputs with expected hashes are checked. The Fabric adapter generates launcher files; it does not simply rename the downloaded loader JAR.

Shim-era Forge installers write a version-named shim at the server root, and the generated `run.sh` invokes it for its Java check. Installation accepts and owns that file only when the launcher names it, so the root shim is never mistaken for a second installation.

Bootstrap adapters also define the launch command, MCDReforged log handlers, output paths, and superseded core metadata that other subsystems require. Installation and workspace observation consume these unified descriptions instead of matching raw bootstrap method values themselves.

Bootstrap output becomes subject to installation's ownership and commit checks. The bootstrap stage does not by itself publish a workspace receipt or authorize removal of unrelated files. Runtime discovery later recognizes installations from their actual members; it is not just a reverse reading of the lock.

A receipt satisfies the bootstrap contract only when it owns every required managed bootstrap output with bootstrap origin and each still matches its accepted baseline. Required outputs are the managed exact outputs the locked contract declares, plus every managed output existing-tree verification attributes, including dynamically attributed ones such as the shim-era Forge root shim. Seed, discard, and bootstrap-only material never needs a receipt entry. A receipt that lacks a required entry is not current, so the next installation restages and reports an existing file as unowned instead of adopting it silently.
