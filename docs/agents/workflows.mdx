title: "Programmatic workflows"
description: "Sequences for creating, adopting, syncing, upgrading, and inspecting a server from an agent or CI job"
---

These recipes assume `lucy` is on `PATH`, the intended workspace is the current directory (except for `create`), and every command receives `--json-compact --no-interactive`. See [Machine interface](/agents/machine-interface) for the stream and failure contract, and [Commands](/commands/global-flags) for human-facing flag semantics.

## Result map

| Command | Changes | JSON result |
| --- | --- | --- |
| `create` | Manifest, lock, optionally runtime files | `kind: "create"`, with install fields plus `workspace`, `non_empty`, `replaced_manifest`, `installed` |
| `init` | Manifest, lock, `.lucy/config.yaml` when missing | `kind: "install"`, `published_config`; `packages` is always empty and `total_packages` is the lock's package count |
| `install` | Lock when stale, runtime files | `kind: "install"`, with `mode`, `reason`, `files`, `fetch`, `diagnostics` |
| `add`, `remove` | Manifest, lock, runtime files | `kind: "install"`, `published_manifest`, package and manifest changes |
| `upgrade` | Manifest, lock, runtime files | `kind: "upgrade"` when applied; `kind: "upgrade-frontier"` for `--dry-run` and JSON `--policy options` |
| `status` | Nothing | `kind: "status"`, `source` is `live` or `lock` |
| `tree`, `leaves` | Nothing | Plain payload with `origin`, either `lock file` or `live probe` |
| `file` mutations | Tracked files, CAS, manifest | Event payload with `operation`, `changes`, `skipped`, `reclaimed` |
| `deinit` | Removes Lucy state | `{ "removed": [...] }`, with no `schema` or `kind` |
| `compile` | Builds a mod JAR | No JSON; screen output is human, stdout carries the artifact path |

`add`, `remove`, `init`, and `install` share the install result. `create` embeds it. `upgrade` reuses it after applying a plan.

## Create a server

```bash
lucy create \
  --directory ./server \
  --minecraft 1.21.4 \
  --core paper \
  --no-install \
  --json-compact --no-interactive > create.json

cd ./server
lucy install --locked --json-compact --no-interactive > install.json
```

`--minecraft` is required when no prompt may open. `--directory` defaults to `.`, and `--core` defaults to vanilla `minecraft`. Use `--no-install` when you want publication and runtime provisioning as separate, observable steps; omit it to install in the same command.

Successful preparation has `installed: false`, `published_manifest: true`, and an absolute `workspace` path. `non_empty` reports whether files already existed, and `replaced_manifest` reports a forced replacement.

If creation fails after the manifest and lock were written, the failure document does not include the partial result. The title distinguishes these cases:

- `the server directory was created but installation failed`
- `the server directory was created but provisioning was interrupted`

The workspace is usable in both cases. Run `lucy install` there to finish. Do not run `create` again with `--force` just to retry the installation; that replaces declared intent.

## Adopt an existing server

```bash
cd /srv/minecraft
lucy init --entry-point fabric-server-launch.jar --json-compact --no-interactive > init.json
lucy install --locked --json-compact --no-interactive > install.json
```

`init` records what is installed; it does not place runtime files in the live server. The following `install --locked` converges the directory against the freshly recorded lock.

When several runtimes share the directory and machine mode cannot ask, `init` fails with `several server runtimes share this directory`. Its `details` list exact `lucy init --entry-point '<path>'` commands, one per candidate. Pick one instead of guessing.

`init` refuses to replace an existing manifest without `--force`. It writes `.lucy/config.yaml` when that file is missing; `published_config` reports whether this happened. A successful `init` has `published_manifest: true`, and its `mode` is `resolve`.

## Add and remove packages

```bash
lucy add modrinth:lithium --json-compact --no-interactive > add.json
lucy remove modrinth:lithium --json-compact --no-interactive > remove.json
```

Pass an explicit `provider:project` reference when you need deterministic input. Bare names are resolved against the current lock first and then a default registry; an ambiguous bare name fails rather than guessing.

`add` and `remove` commit the manifest, lock, and runtime changes as one transaction. A failed resolve leaves the documents unchanged. Check `published_manifest`, `published_lock`, and `packages[].change` rather than assuming a file count.

`--with-optional` on `add` permanently records the selected optional packages in `lucy.yaml`; it is not a one-run overlay. `--locked` works only when the requested result is already represented in the current lock. `--offline` requires the necessary artifacts to be present and hash-correct.

## Replay a locked server

```bash
lucy install --locked --offline --json-compact --no-interactive > install.json
```

Use this in CI when `lucy.yaml` and `lucy-lock.yaml` are committed and the artifacts are in the global cache. `--locked` fails when the lock is missing or stale; it never silently re-resolves. `--offline` fails when an artifact is missing, not cached, or hash-mismatched. Warm the cache online first if needed; `lucy cache clear` removes the global cache, not workspace files.

A successful replay normally has `mode: "replay"`, `published_lock: false`, and zero or more `files` changes. Exit status `0` means the workspace converged, not that every count is zero. Check `files` and `packages` when you need evidence of change.

## Upgrade with a plan

Applying an upgrade in machine mode does not ask for confirmation. Always read the frontier first:

```bash
lucy upgrade --all --dry-run --json-compact --no-interactive > frontier.json

jq -r '.frontier[] | [.hash, .metrics.upgraded_roots, .metrics.version_bumps] | @tsv' frontier.json

lucy upgrade --all --policy <sha256:...> --json-compact --no-interactive > upgrade.json
```

`--dry-run` returns `kind: "upgrade-frontier"` even when a policy is supplied. Each frontier entry carries a `hash`, `metrics` (`upgraded_roots`, `version_bumps`), and a nested `result` that shows the planned package and manifest changes. `selected_hash` names the policy's default choice.

Apply one plan by passing its hash to `--policy` together with `--all`. `--policy more` and `--policy later` are also valid; `--policy options` is an interactive selection and, in JSON mode, returns the frontier instead of applying anything. An applied result has `kind: "upgrade"`, plus `policy`, `plan_hash`, and the usual install fields.

Upgrade requires a current lock and refuses when the manifest changed since that lock. It advances package roots; it does not change Minecraft, the server core, or the MCDReforged runtime.

## Inspect without changing state

```bash
lucy status --json-compact > live.json
lucy status --from-lock --json-compact > lock.json
lucy tree --json-compact > tree.json
lucy leaves --json-compact > leaves.json
lucy java list --json-compact > java.json
lucy file list --json-compact > files.json
```

- `status` without flags observes the live directory. An empty, ambiguous, or undeclared workspace can still be a successful report; inspect `server`, `packages`, and `warnings` instead of relying only on the exit status.
- `status --from-lock` renders only the lock. It fails with `status.lock_missing` when there is no lock and leaves `activity` as `unknown` because the lock cannot prove runtime state.
- `tree` and `leaves` read the lock by default and fall back to a live probe when the lock is missing or invalid. Their `origin` field tells you which source was used. Add `--live` to force observation.
- `java list` reports the locked requirement, the selected runtime, every installed runtime, and each runtime's problems. It still lists runtimes when no lock exists.
- `file list` is read-only. A modified immutable file produces a warning and suggests `lucy file update` or `lucy file recover`.

## Read errors in a workflow

Do not retry every failure. Match the `code` and the exact title first; [Workflow diagnostics](/agents/diagnostics) maps both to the evidence to collect. The most common workflow recoveries are:

- Creation failure after publication: run `lucy install` in the reported workspace.
- `lucy.yaml exists; use --force to replace declared intent`: inspect the existing manifest and use `init` to adopt it, or pass `--force` only when replacement is intended.
- Locked installation failure: resolve once without `--locked`, inspect the new lock, and commit it.
- Concurrent writer failure: wait for the other process; never retry in parallel.
