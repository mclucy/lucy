title: "Versions and module constraints"
description: "Version dialects, package selectors, and descriptor dependency checks"

Lucy handles two different questions: selecting a registry artifact for a declared package, and checking whether the modules in the selected artifacts satisfy loader metadata. A package selector may name a version, release ID, file ID, or filename. A module dependency instead names a loader-visible module and a constraint written in that descriptor's dialect. A registry project name and the module ID it provides can differ.

## Dialects

Version engines bind parsing, ordering, and matching to a specific dialect. Fabric descriptors use the Fabric grammar; Quilt descriptors use the Quilt constraint grammar, whose concrete versions are Fabric version values so Quilt and Fabric modules compare directly; MCDReforged plugin metadata uses MCDR; Forge and NeoForge `mods.toml` use Maven; Minecraft has its own release and snapshot grammar; opaque identifiers use equality semantics. Versions from different dialects are not comparable.

A version value can hold a floating selector such as `any`, `stable`, or `beta` during selection. Parsing a concrete version rejects those selectors. An empty constraint or `*` accepts any version; an invalid expression is an error rather than an unconstrained match. Constraint expressions are alternatives of conjunctions: one alternative must have all its terms satisfied. For Fabric version arrays, each array element is an alternative. Fabric non-semantic versions have special equality-based matching rather than ordinary numerical ordering.

## Candidate selection

Candidate resolution scopes project requests by environment, ecosystem, provider, and project. Enabled requirement bindings apply hard filters to candidates, including selector, channel, and file pattern; without a file pattern lucy selects primary files. Release hints supplied by upstream dependency metadata affect candidate ordering, not eligibility by themselves. Previous pins can be preferred when they still satisfy the request.

Downgrade orders package labels using the ordering used by upgrade checks, not publication dates or descriptor-module versions. It counts complete labels strictly below the locked version, including each prerelease suffix. Multiple artifacts with the same label count once; the newest publication represents that label, with repository identifiers breaking ties. The chosen artifact is the project's only candidate for that resolution, so neither another label nor another artifact can substitute. The existing file pattern or primary-file rule still filters eligibility, but the old selector's channel restrictions do not. Opaque versions cannot be downgraded, and an unparseable locked version cannot serve as a baseline.

Candidate resolution and descriptor validation are related but distinct. Registry dependency metadata can identify other projects to select; descriptors establish module IDs, dependency constraints, and bundled modules in the actual artifact. A release that appears suitable at the registry layer can therefore fail when its modules are checked against the selected runtime and other artifacts.

## Module graph

The resolver indexes modules by environment, module namespace, and normalized module ID, including aliases declared through `provides`. The ecosystem table decides the namespace: a runtime that loads several descriptor ecosystems resolves all their modules in one graph, so on a Quilt server Quilt and Fabric modules share one namespace, and on a Paper server Paper and Bukkit plugins do. Every other ecosystem keeps its own namespace. The same table orders the descriptors that loader prefers when one artifact carries several. Native modules take precedence over bundled copies; two native modules from different packages claiming the same identity are ambiguous. Competing bundled copies are compared by their version dialect, and incomparable versions cannot be arbitrarily ordered.

A descriptor dependency is a tree. A node names one module and a constraint; its any-of alternatives can satisfy it instead, its all-of nodes must also hold, and a holding unless condition waives it. A waived break does not apply. An absent optional alternative satisfies its any-of group, and a requirement whose only candidate is client-only is waived, because the loader filters that candidate out of a dedicated server. Checking variants against the runtime alone and checking the complete graph use the same evaluator.

The runtime can provide modules itself, including Minecraft and loader components. Module dependency checks consider those runtime modules and selected package modules. Required dependencies and incompatibilities produce problems when unsatisfied; Java is handled separately by [Java runtime architecture](/agents/java-runtime). Module problems can lead the resolver to reject candidate combinations. A rejection ledger groups candidate failures by project and reason; a search limit is not proof that every possible combination was explored.

During candidate search, a package whose descriptor ecosystem the runtime prefers can stand in for a dependency package of a later ecosystem when it answers every module identity of that package and the selected constraints accept the versions it exposes, such as Quilted Fabric API for Fabric API on a Quilt server. A pure dependency demand then binds to that package instead of installing a second native module with the same identity, and its dependents move onto it. Substitution is part of the backtracking state, so an abandoned branch takes its substitutions and exact-release pins with it. Direct requirements and dependencies named by an exact release are never substituted.
